Acta.Acta: durable background jobs for .NET

acta, n. pl. · Latin: the things that have been done; the official record of proceedings.

Durable background jobs for .NET.

Kill the worker. Keep the work.

What

Enqueue, schedule, retry, and wait on work that survives crashes and deploys. Every job is a row in the Postgres, SQL Server, or SQLite you already run, with fan-out, recovery, a dashboard, and a CLI built in.

Why

Because production happens: workers die holding work, retries repeat side effects, jobs get "stuck" and nobody can say why. Acta makes every job, attempt, lease, and retry durable SQL state you can see, query, and act on: no broker, no sidecar, no workflow SaaS.

The code

A job that survives crashes, in a dozen lines of C#.

The [Job] name is the durable, operator-facing contract; enqueue is typed, dispatch is source-generated. And the state it creates isn't hidden in a broker or a SaaS console: it's rows you SELECT.

C# · the whole contract
public sealed record DeliverWebhook(Guid DeliveryId, Uri Endpoint, string Payload);

public sealed class WebhookJob(IWebhookSender sender)
{
    [Job("deliver-webhook")]
    public Task Handle(DeliverWebhook input, CancellationToken ct) =>
        sender.SendAsync(input.Endpoint, input.Payload,
            idempotencyKey: input.DeliveryId.ToString(), ct);
}

// enqueue from anywhere in the host
await jobs.EnqueueAsync(new DeliverWebhook(
    Guid.CreateVersion7(),
    new Uri("https://partner.example.com/hooks/orders"),
    """{"orderId":"ORD-1042","status":"shipped"}"""), ct: ct);

How it runs

How one worker claims, runs, and finalizes a job.

Done means committed

A job is done when its completion is a committed row, not when the handler returns. A crash before that commit runs the job again; a crash after it never loses it.

Durable, and still fast

Completions that arrive while the finalizer is writing go out in the next commit, up to 128 at a time, so durability does not cost a commit per job. One box drained 23,349 jobs a second on PostgreSQL. Engine round

Bounded, and it heals

A slow database stops intake instead of filling memory. A worker renews only the rows it holds, so when one dies its rows run out their lease and any peer takes them.

Optional Redis only rings the bell so idle workers wake sooner: SQL remains the only durable truth.

Different domains, one shape

No domain types: a step may call a model, a payment rail, FFmpeg, or a machine. What these share is work measured in minutes or days, expensive to repeat, and unacceptable to lose.

How it compares

How Acta compares with Hangfire, Quartz.NET, TickerQ, MassTransit, and Temporal.

This table is the short version. The full fit guide covers when to keep exactly what you have. Choosing Acta

Hangfirebackground jobs
Keep Hangfire when its familiar persistent job runner is enough. Consider Acta when job state should become first-class application data, with durable steps, signals, lineage, and curated SQL inspection. Migration notes
TickerQsource-generated scheduler
Keep TickerQ when you want a source-generated scheduler with persistence, dashboard tooling, chaining, priorities, and concurrency controls. Consider Acta when SQL must serve as the durable operational ledger for resumable work: checkpoints, signals, recovery evidence, and operator intervention. Migration notes
Quartzscheduling
Keep Quartz when calendar sophistication, cron behavior, and misfire handling are the main problem. Consider Acta when the execution lifecycle matters more than the calendar: durable steps, leases, waits, recovery, lineage, and operator controls. Migration notes
Temporal / Dapr Workflow / Durable Taskreplay engines
Keep a replay engine when deterministic event-history replay and orchestration semantics are requirements. Consider Acta when you want ordinary re-entrant .NET handlers with no determinism contract, checkpoints instead of replayed history, and application-owned SQL state. The longer answer
A message busMassTransit, NServiceBus, …
Keep a message bus when you need distributed messaging, pub/sub, transport abstraction, or endpoint contracts. Consider Acta when the problem is recording and operating the lifecycle of application-owned work rather than moving messages between systems.
DIY queue table+ hosted service
Keep a DIY queue table when enqueue, claim, and complete are genuinely enough, and you are prepared to own its failure modes. Consider Acta before adding leases, retries, schedules, recovery, operator controls, a dashboard, and deterministic testing yourself.

The dashboard

A built-in dashboard shows what every job is doing.

The embedded dashboard reads the same durable rows you can query yourself (backlog, failures, dead workers with heartbeats, next schedules) and says what needs action. It ships inside your app as a library, local-only by default (browse to it as localhost or 127.0.0.1), with mutating verbs off until you enable them; removing the local-only guard without configuring authorization does not degrade, it refuses to start.

Capabilities · quick reference

Everything Acta includes, at a glance.

The one-line version of everything Acta does. Each is explained, with the API behind it, in the guide.

Jobs & scheduling

  • Fire-and-forget · delayed · recurring under one model
  • Durable retries with typed backoff: policy, not folklore
  • Persistent schedule cursors: missed windows explicit; one stable job row
  • Deduplication keys stop blind repeats at enqueue
  • Atomic enqueue with your data: one transaction, or the external outbox

Execution primitives

  • Named durable steps: recorded outcomes return on re-entry
  • AtMostOnce(): record intent before invocation; reconcile an interruption
  • Durable sleeps & signals: wait days, hold no thread
  • Checkpoint slots: resume with intermediate results
  • Child jobs: fan-out / fan-in, lineage
  • Lanes: strict order per key; only the head is claimable
  • Concurrency keys, limits & locks
  • Rate limits: 600/m per definition, one meter per key

Failure & recovery

  • Leases with automatic lapse: leaderless reclaim & retry
  • Survives crashes, rolling deploys, restarts: two builds share a namespace, a rollback just works
  • Explain: a job tells you why, and what next
  • Restart month-old failures with stored input
  • Failure alerts: queryable rows

Visibility & ops

  • Everything SQL-visible: with curated operator views
  • Append-only event ledger per job
  • Embedded dashboard: an operational tool
  • CLI in every host: incl. jobs debug under a breakpoint
  • Opt-in controls: pause, cancel, restart, signal
  • Namespaces & tenants: who runs the work, who it is about

Engineering quality

  • pg · mssql · sqlite: one operational model
  • Generated dispatch, NativeAOT, no reflection
  • 1 SQL round-trip per state change
  • Deterministic test host: real-DB tests in tens of ms
  • Typed contracts: [Job] is the durable name
  • Redis as a bell only; pluggable payload serializers
  • Anvil lab: a million jobs, kill workers, watch recovery
