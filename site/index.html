Four examples: a plain background job, order completion, recurring synchronization, and PDF approvals with parallel child jobs.

The smallest job is a method: an attribute, its input, and a cancellation token. One line enqueues it, and from that line on the job is a row you can read.

C# · the job, and the line that enqueues it
[Job("send-welcome-email")]
public Task Send(WelcomeEmail email, CancellationToken ct) =>
    mail.SendWelcomeAsync(email.To, email.Name, ct);

// From a controller, a handler, anywhere in the app:
await jobs.EnqueueAsync(new WelcomeEmail(user.Email, user.Name));
SQL · the row that line wrote
SELECT job_status, failure_count, next_run_at_utc
FROM acta.jobs_view
WHERE definition_name = 'send-welcome-email';
  1. readyjob_statusRight after the enqueue. The row is there before any worker runs, with the input stored on it.
  2. executingjob_statusA worker claimed the job and holds a lease on it. If that worker stops, the lease lapses and another worker takes the job.
  3. succeededjob_statusThe method returned. The row stays as the record of what ran.
  4. readyfailure_count 1The send threw instead. The row is ready again, and next_run_at_utc says when it is tried, after a backoff, up to the job's MaxAttempts.

At least once. A retry or a takeover runs the method again, so make the send safe to repeat: give the mail provider a key it deduplicates on.

Book a shipment, confirm payment, issue the invoice, then send its receipt. Each operation waits for the one it depends on. An unconfirmed booking stops the job before charging or invoicing.

C# · order completion with explicit dependencies
[Job("process-order")]
public async Task Process(Order order, JobContext ctx, CancellationToken ct)
{
    var booking = await ctx.RunStepAsync("book-shipment",
        c => shipping.BookAsync(order.Id, $"booking:{order.Id}", c), ct);

    if (!booking.Confirmed)
    {
        await ctx.FailAsync("Shipment booking was rejected", ct);
        return;
    }

    var charge = await ctx.RunStepAsync("charge-card",
        c => payments.ChargeConfirmedAsync(order, $"payment:{order.Id}", c), ct);

    var invoice = await ctx.RunStepAsync("issue-invoice",
        c => invoices.IssueAsync(order.Id, booking.Id, charge.Id,
            $"invoice:{order.Id}", c), ct);

    await ctx.RunStepAsync("send-receipt",
        c => mail.ReceiptAsync(invoice.Id, $"receipt:{invoice.Id}", c), ct);
}
  1. book-shipmentsteps_viewRecords the booking outcome. A rejected booking ends the job; charging, invoicing, and receipt delivery cannot run.
  2. charge-cardsteps_viewRuns after booking is confirmed. The payment adapter returns only a confirmed charge; a decline or transient error throws, so no invoice is issued.
  3. issue-invoicesteps_viewReceives both the confirmed booking ID and charge ID. On replay, completed steps return their saved results.
  4. send-receiptsteps_viewStarts only after the invoice exists. The stable invoice ID gives receipt delivery the same deduplication key on every retry.

Application contract. This example starts with a validated order whose stock is already reserved. Each external adapter must honor its operation key. The payment adapter must throw unless a charge is confirmed. Booking cancellation, stock release, and refunds need explicit business recovery paths when an order cannot finish; Acta does not roll back external operations.

One job keeps a local copy of a web shop's orders current: each firing reads where the last one stopped, applies the next batch, and writes the new position back.

C# · the handler, simplified from the lab
[Job("sync-orders")]
[Schedule("every-5s", "PT5S")]
public async Task Sync(JobContext ctx, CancellationToken ct)
{
    var watermark = await ctx.GetVariableOrDefaultAsync("watermark", 0L, ct);
    var changes = await shop.ChangesAfterAsync(watermark, 40, ct);
    if (changes.Count == 0) return;   // up to date until the next firing
    await store.ApplyAsync(changes, ct);   // an upsert: a replay lands once
    await ctx.SetVariableAsync("watermark", changes[^1].ChangeId, ct);
}
  1. sync-ordersjobs_viewOne permanent job that the schedule fires again and again, Idle between firings.
  2. every-5sschedules_viewThe schedule and its next occurrence, which you can pause, resume, or trigger now.
  3. watermarkcheckpoints_viewA variable that outlives the firing, the retry, and the worker.

Stop the worker mid-batch, with a deploy or a kill, and the next one picks the job up at the same watermark; a replayed batch is an upsert, so it lands once.

Build a manuscript's proof PDF and check its references in parallel child jobs. Request review, wait for author and editor approvals of that exact proof, then publish it.

C# · PDF production and human approvals
[Job("publish-manuscript")]
public async Task Publish(
    Manuscript manuscript, JobContext ctx, CancellationToken ct)
{
    var proofId = await ctx.GetOrSetVariableAsync(
        "proof-id", Guid.NewGuid, ct);

    var prepared = await ctx.ParallelAsync("prepare", p => p
        .Child("pdf", new BuildProofPdf(manuscript.RevisionKey, proofId))
        .Child("references", new CheckReferences(manuscript.RevisionKey)),
        ct);

    prepared.ThrowIfAnyFailed();

    await ctx.RunStepAsync("request-review",
        c => proofs.RequestReviewAsync(proofId, c), ct);

    foreach (var role in new[] { "author", "editor" })
    {
        var approval = await ctx.WaitSignalAsync<ProofApproval>(
            $"{role}-approval", TimeSpan.FromDays(14), ct);

        if (approval is not { Approved: true } || approval.ProofId != proofId)
        {
            await ctx.CancelAsync("This proof was not approved", ct);
            return;
        }
    }

    await ctx.RunStepAsync("publish",
        c => proofs.PublishAsync(proofId, c), ct);
}
  1. proof-idvariableCreated once and stored for this job. Every retry, child job, approval request, and publication uses the same proof identity.
  2. prepareparallel childrenBoth children read the same immutable manuscript revision independently. PDF creation and reference validation must both succeed before review is requested.
  3. request-reviewstepCreates the review request after preparation completes. Its operation key is the proof ID, so replay cannot create a second request.
  4. author / editorsignal waitsEach reviewer has 14 days from when their wait first begins. The stored deadline survives retries and restarts. The job releases its worker while waiting; a timed-out wait cancels the job and prevents publication. Both approvals must name this proof ID.
  5. publishstepPublishes the exact stored PDF that was approved. The publishing adapter must be idempotent by proof ID.

Application contract. One job handles one immutable manuscript revision. ProofApproval carries ProofId and Approved. The PDF child stores a complete, immutable artifact before succeeding; the reference checker fails its child job if validation does not pass. Corrections start a new proof workflow. Review and publication adapters must deduplicate by proof ID. The 14-day timeout is an illustrative policy for each reviewer separately, not one deadline for the whole approval process.
