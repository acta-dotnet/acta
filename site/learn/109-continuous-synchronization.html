How to keep another system in sync with a permanent job

One permanent job calls a service on a schedule and keeps a watermark of how far it got. Each firing syncs one bounded batch and returns; the watermark is the job's own durable variable, read at the top of every execution, so a recovered firing continues where the lost one stopped.

A how-to for Acta, durable execution for .NET. New to Acta? Run your first durable job in five minutes.

Read as

1Fire the job on a schedule

The schedule fires the one permanent job every five seconds. A firing does one bounded batch and returns, so between firings the job is Idle and holds no thread.

2Read the watermark and ask for what changed after it

The call to the service is a bare line on purpose: a read is safe to repeat, and on a permanent job a step would answer from an earlier firing's record. A firing that finds nothing returns; the next one comes on schedule.

3Let the service hand out its changes in a fixed order

The pattern needs one thing from the service: changes come in a fixed order, and a caller can ask for the ones after the last one it saw. An API with a since or a cursor parameter fits the same way.

4Save the work first and the watermark after

The orders land first and the watermark after them: an attempt that dies between the two replays one batch, which the upsert absorbs; the other order would skip one.

5Make the save an upsert that keeps the newer change

A batch applied twice then changes nothing. The statement is SQLite's; write the same keep-the-newer upsert in your own database's dialect.

Remember

  • Never loop forever inside the handler and never poll from it. A firing that finds nothing to do returns, and the next firing comes on schedule.
  • The watermark is a durable variable on the job. Acta carries it across firings, retries, and workers, so no table of your own has to remember how far the sync got.
  • The service has to hand out changes in a fixed order and keep them. For a source that fires once or forgets, capture it into a durable feed of your own first.
  • Firings that came due while no worker ran are skipped, not queued. The next firing reads the watermark and catches up by itself.
  • With the default heartbeat, a killed worker's firing comes back three to about seven minutes after its last heartbeat; on SQLite a restart brings it back at once. The lab shortens the heartbeat so you can watch.
  • A sync that writes back to the other system needs that system's idempotency key, so a repeated batch does not act twice there.

Check yourself

The worker is killed right after a batch was saved and the watermark written. What does the next execution do?

Show the answer

Reads the watermark the dead attempt wrote and applies the next batch. The next worker, or the same one restarted, reclaims the firing, runs the handler from its first line, and reads the watermark. Same job, same firing, one more execution number.

An attempt dies after the orders were saved but before the watermark moved. What happens to that batch?

Show the answer

It is applied a second time, and the upsert changes nothing. The retry reads the old watermark and gets the same changes. Each order keeps only a newer change than the one it holds, so the replay leaves the data as it was.

The lab behind it: one permanent job keeps an external system synchronized

This program is an Engineering Lab: beside the how-to it prints the rows that show what happened, and its notes weigh the design against the alternatives.

The problem

An application has to stay current with an external system, a web shop here, that publishes changes faster than anyone wants to poll by hand: orders are created, paid, and shipped all day. The usual answer is a loop in a hosted service with a timer, a retry policy, a table that remembers how far the loop got, and a prayer that the process is running. When the process dies mid-batch, the loop's in-memory position dies with it, and nothing says whether the last batch landed.

Common approaches

  • A BackgroundService with a PeriodicTimer: progress lives in memory or in a hand-maintained table, and nothing records what each run did.
  • A queue that fans out "sync now" messages to workers, plus a state table, plus a scheduler to enqueue them.
  • A platform cron that starts a process per tick, which must find its own position and never overlap the previous tick.
  • A workflow engine with a long-running activity that loops forever.

Why this design

One permanent job, sync-orders, with one schedule, every-5s, and one durable variable, watermark. The handler, as SyncOrdersJob.cs has it without its console lines and the lab's crash switch:

The web shop is a simulator: an append-only table of order changes in the lab's own SQLite file, beside the local orders and Acta's tables, seeded the same way on every machine. The handler reads it through ShopFeed as it would read a remote API, never through Acta.

The schedule admits a firing onto the permanent job every five seconds; the firing applies one batch of forty changes and returns; the job then sits Idle until the next admission, holding no thread. The watermark, the id of the last shop change applied, is a variable on the job. Acta keeps it the way it keeps the job itself: a row in checkpoints_view, carried across firings, retries, and workers, and the handler reads it at the top of every execution. Nothing else remembers how far the sync has come: no table of the application's, no field, no loop.

That is what makes the crash boring. When the worker dies after a batch, the next worker, or the same one restarted, reclaims the firing through the lease, re-enters the handler from the top, reads the watermark the dead attempt wrote, and applies the next batch. The same job identity, the same firing id, one more execution number.

Acta's own progress is separate. The schedule cursor says when the job is next due, and the firing envelope says which schedule admitted the firing and how it settled. A firing that finds nothing to sync still moves the cursor and leaves the watermark alone; a manual trigger moves the watermark and leaves the cursor alone.

Trade-offs

Execution is at-least-once, and the handler is written for it. The orders land in the store's transaction and the watermark in Acta's, one after the other, so an attempt that dies between the two is run again and replays one batch; the upsert keeps only a newer change per order, so the replay changes nothing. Written the other way round, watermark first, a death between the two would skip a batch. A sync that writes back to the external system needs that system's idempotency key, as the agent guide's webhook sample shows.

A full resync is a reset: ctx.ResetStateAsync() as the handler's final action clears the watermark with the rest of the job's state, and the next firing starts from change 0, where the upsert lands every change once more. The lab never needs it, so it never calls it.

The feed's contract carries the correctness: change ids only grow, changes come back in id order, and none is ever deleted. A source without ordered, retained change tracking cannot be synchronized by watermark, and this lab does not pretend otherwise.

Run the experiment

Everything runs on embedded SQLite from a fresh clone; the lab keeps its own database file. The first command runs the whole story through three firings and exits; the rest reproduce the crash by hand, in two terminals, with a real process kill (Environment.FailFast). The tests in 804-continuous-synchronization-tests prove the same recovery inside one process instead, by expiring the lease and fencing the late attempt, and Acta's release validation kills worker processes at scale.

outage switches the shop feed off and on again: a firing that cannot read the feed fails its attempt, the ledger records job.execution-failed, and Acta retries it under the job's budget (MaxAttempts = 3, two seconds apart); a spent budget settles the firing as failed and returns the job to Idle, and the next scheduled firing syncs as soon as the feed is back. The watermark is untouched by a failed attempt, so nothing is lost and nothing is applied twice.

The lab shortens the heartbeat to one second, so the lease is four seconds and the restarted worker recovers within about ten; production keeps the default forty-five seconds.

After the tour (step 1). Three firings synced 120 changes in three batches of forty, and the job is back to Idle with no lease; the cursor already names the next occurrence, the envelope records how the last firing settled, and the watermark sits on the job as a variable.

jobs_view is one row for the whole run: the same job_ref, one more execution_number per firing. schedules_view is Acta's progress, the cursor and when the engine looks again. checkpoints_view holds both the firing envelope under sys.firing, the schedule that admitted the firing, its occurrence, and the firing's settlement, and the handler's watermark under its own name, kind variable, written by SetVariableAsync and nowhere else. The ledger alternates an admission and a settlement per firing; an admission row carries the execution number the job had when it was admitted, so the one that opened execution 1 reads 0. The last line is the destination, the one table that is the application's.

The rows the dead process left behind: the job still executing under a lease nobody will renew, the envelope still pending, the watermark at the batch the dead worker applied, and the feed twenty changes ahead of it.

After the restart (step 6). The restarted worker found the killed worker's process gone, released its lease and reclaimed the firing, and the claim ran it as execution 8 of the same job and the same firing. No admission sits between the reclaim and execution 8, so execution 8 ran the firing execution 7 lost, not a new one; the envelope that was pending under execution 7 settled under execution 8. schedule.skipped is the misfire policy at work: the occurrences that fell due while no worker ran were skipped, not queued, which is the default and the right one for a controller that catches up by itself. Event 22 admits the next firing, with an id of its own. Nothing was applied twice: the destination holds forty orders at change 180, one row per order, and the watermark equals the feed's head.

Break it

Move crash.AfterBatchAsync in SyncOrdersJob.cs between store.ApplyAsync and ctx.SetVariableAsync and arm a crash: the orders hold the batch, the watermark does not, and the recovered firing applies the same batch again, which the upsert absorbs. That is the replay at-least-once allows, and the reason the orders land first. Then swap the two lines so the watermark is written before the orders, and crash between them: the recovered firing starts after a batch the orders never received, forty changes short, which is the bug. Finally drop the WHERE excluded.last_change_id > local_orders.last_change_id clause from the upsert and replay a batch: an older change overwrites a newer order, which is what the clause is for.

When not to use

  • A source that publishes changes without a stable order or that forgets them (a webhook that fires once, a feed that compacts). Watermarks need the contract above; capture such a source into a durable feed of your own first.
  • Work where each occurrence is its own business event with its own retries, result, and retention: a nightly statement run, an hourly import whose files must each be tracked. That is a PerOccurrence definition, one ordinary root job per occurrence, not a permanent job.
  • A sync that must write back to the external system: still a permanent job, but every write needs the external system's idempotency key, as in the agent guide's webhook sample.
