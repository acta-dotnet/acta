How to wait for an approval without holding a worker

A job parks on a named signal, holds no worker, and carries on when the signal is raised.

A how-to for Acta, durable execution for .NET. New to Acta? Run your first durable job in five minutes.

Read as

1Wait for a named signal in the handler

WaitSignalAsync stores the wait as a row and ends this execution. The job reads suspended. Suspends (no executor held) until the named signal is raised, then re-enters with the latched payload.

2Raise the signal when the answer arrives

Whoever learns the answer raises the signal by name on that job: an endpoint, another job, an operator. The value is stored, the job becomes ready, and the handler runs again from its first line. This time the wait returns the stored value.

Remember

  • A suspended job is healthy. It is waiting, not stuck.
  • The handler starts from the top when the signal arrives. Put work that must not repeat in a step.
  • Decide what happens if nobody answers: WaitSignalAsync<Decision>("approval", TimeSpan.FromDays(14), ct) returns an outcome whose TimedOut is true when the deadline passed.
  • A raise proves nothing about who sent it. Check the caller in your endpoint before you raise.
  • A raise that comes before the handler reaches its wait is stored, and the wait reads it without parking.
  • The typed value is null when the signal was raised without one. A value binds leniently, so give an enum a first value that grants nothing.
  • A signal keeps the value of its first raise. Keep timestamps and per-attempt ids out of it, so a repeated raise answers AlreadyInState.

Check yourself

While the job waits for the signal, which worker holds it?

Show the answer

No worker. The wait is a row. The job reads suspended with no worker and no lease, so the process can stop and the wait is still there.

The signal is raised. On which execution does the job finish?

Show the answer

Execution 2, from the first line of the handler. Acta does not resume in the middle of a method. It runs the handler again, and the wait answers from its stored value.

The lab behind it: waiting is a row, not a worker

This program is an Engineering Lab: beside the how-to it prints the rows that show what happened, and its notes weigh the design against the alternatives.

The problem

A job may wait hours or days for a person or another system. Keeping a task alive consumes capacity and still loses the continuation when the process stops.

Common approaches

  • Block a task and hold process-local state.
  • Poll until the external condition becomes true.
  • Self-reschedule when the job can check readiness itself.
  • Latch an explicit signal when another actor knows the event happened.
  • Delegate a large externally orchestrated process to a workflow engine.

Why this design

WaitSignalAsync writes a named checkpoint and ends the execution. The worker lease is cleared. Raising the signal stores its payload and re-arms the same job; the handler re-enters and reads the latch, which stays set for any later replay.

Trade-offs

The handler starts from the top on execution two. Only durable steps and checkpoints suppress repeated work. Signals also require a reliable actor to raise the correct named latch and a policy for signals that never arrive.

Break it

Run a real two-process recovery against one configured database:

start stops after suspension. inspect starts no worker and proves that the exact identity remains suspended and unleased. raise does not enqueue another job; it signals that identity and waits for its second execution to finish.

When not to use

Use rescheduling instead when the job owns the readiness check. Use polling when the source cannot emit a signal and the load is acceptable. Prefer a workflow product for very large, externally authored, human-centric processes.
