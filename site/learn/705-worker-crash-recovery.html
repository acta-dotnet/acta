How to recover the work of a killed worker

A worker process is killed in the middle of a job, and another worker reclaims the job once its lease has lapsed. The program runs on PostgreSQL or SQL Server.

A how-to for Acta, durable execution for .NET. New to Acta? Run your first durable job in five minutes.

Proven by other suitesLab learn/700-topology-and-deployment/705-worker-crash-recovery
Read as

1Give the job a retry budget, because a crash spends an attempt

Nothing in the handler recovers the job. A worker that dies stops heartbeating, the lease on its job lapses, and another worker reclaims the job as a failed attempt and runs it again.

2Shorten the heartbeat only to watch the recovery

One knob shortens the whole coordination triple in proportion: a 1s beat gives a 4s lease and a 7s dead-worker window, which is what makes the kill below observable in seconds instead of minutes.

Remember

  • Run it in four terminals against one PostgreSQL or SQL Server database, each with dotnet run --project learn/700-topology-and-deployment/705-worker-crash-recovery -- <mode>: worker-a, enqueue, inspect, then worker-b. With no mode the program prints these commands and exits.
  • On SQLite a restart brings a lost attempt back at once: a starting worker releases the work of processes on the same machine that have ended. A server database waits out the lease: three to about seven minutes with the default heartbeat.
  • The reclaim is job.execution-orphaned on the timeline, with the reason lease-expired, or process-ended after a SQLite restart.
  • A crash counts against the retry budget, and a reclaimed job is due again at once, without the backoff.
  • A job that is waiting or sleeping holds no lease and needs no recovery.
  • The name in [Job("crash-recovery-probe")] is stored with every job. Treat it as permanent once jobs exist under it: a job stored under a name no handler carries stays Ready, and nothing runs it.
  • CrashRecoveryProbe is stored with each job as its input. Add a field as optional or with a default. A renamed, removed or retyped field needs a new job name such as crash-recovery-probe-v2, and the old handler stays registered until its jobs have finished: Change a job's input without breaking the jobs already stored.
The lab behind it: SQL-backed crash recovery without a leader

This program is an Engineering Lab: beside the how-to it prints the rows that show what happened, and its notes weigh the design against the alternatives.

The problem

Replacing a broker means the database must handle claim races, ownership, leases, dead workers, and replay after the process disappears at the worst moment.

Common approaches

  • Use a broker for delivery and keep execution state elsewhere.
  • Elect a coordinator or run a dedicated recovery control plane.
  • Let peer workers coordinate through one relational authority.
  • Use an in-process queue and accept loss on restart.

Why this design

Acta's claim, worker heartbeat, lease, and recovery transitions are SQL operations. Recovery rides every worker's heartbeat: the heartbeat that finds the namespace's pass due runs it, so no worker is a permanent leader. The lab kills worker A mid-attempt and lets worker B recover the same durable identity.

Trade-offs

Claim and completion traffic consume database capacity and compete with application traffic. Lease recovery is at-least-once, so handler work can repeat. This design targets application jobs, not high-throughput event streaming.

Run the experiment

This is intentionally a real distributed-provider lab, since its two workers run at once. One SQLite host recovers across restarts without waiting out the lease: its next start finds a predecessor on the same machine whose process has ended, marks it dead, and reclaims its job at once, as 220 shows with its crash and recover runs. Set ACTA_LOCAL_PROVIDER=postgres or sqlserver plus ACTA_TEST_PG/ACTA_TEST_MSSQL, then use separate terminals:

Worker A intentionally exits non-zero. Both workers run short lab-only lease timings, and worker B's heartbeat runs the real recovery pass after expiry. Starting worker A creates a new local session token; enqueue, inspect, and worker B reuse it. Worker A crashes only the probe carrying that token, so an unfinished probe from an aborted older session cannot terminate the new experiment. Each enqueue also updates a local current-job marker, making the sequence repeatable against the same shared database.

Rows to inspect

Run with --all-columns to execute the visible SELECT * Explore query first. The default Notice queries select the fields that prove the lesson, and the text below explains their meaning.

jobs_view moves from executing under A to done under B with a higher execution number. workers_view is filtered to the current session's deployment versions and preserves its heartbeat/liveness evidence, while events_view records the orphaned attempt with reason lease-expired. Application code should use IJobs; the views are curated operator surfaces.

Break it

Start two worker-B processes before recovery and observe that only one claims the recovered row. Move a non-idempotent side effect before worker A's crash and observe why recovery cannot promise exactly once.

When not to use

Use a broker or log when event throughput, fan-out, replayable streams, or independent consumer offsets are the primary problem. Use a dedicated workflow/control plane when recovery authority must be separate from application workers.
