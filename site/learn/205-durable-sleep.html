Remember

  • Task.Delay holds a worker and dies with the process. A durable sleep frees the worker and survives a deploy.
  • Bare code before the sleep runs again when the job wakes. Put work that must not repeat in a step.
  • The job wakes as precisely as the database clock and the worker's polling allow, not to the millisecond.
  • To start a whole job later, instead of pausing inside one, see run a job once, later.
  • "cool-down" names the timer a follow-up sleeps on. A renamed timer is a different timer, so let the sleeping jobs finish before you rename it.
  • A job that waits for a signal or a timer can stay stored for days. The name in [Job("send-follow-up")] is stored with every job. Treat it as permanent once jobs exist under it: a job stored under a name no handler carries stays Ready, and nothing runs it.
  • SendFollowUp is stored with each job as its input. Add a field as optional or with a default. A renamed, removed or retyped field needs a new job name such as send-follow-up-v2, and the old handler stays registered until its jobs have finished: Change a job's input without breaking the jobs already stored.

Check yourself

The job sleeps once and then finishes. How many times does the line handler entered print?

Show the answer

Twice. The line stands before the sleep and outside any step, so it runs on the first execution and again when the job wakes and the handler starts from the top.

The app is stopped an hour into a three-day sleep and started again the next morning. What happens to the job?

Show the answer

Nothing is lost: the due time is a row, and the job wakes when it comes. The due time is stored once, in the database. Any worker that is running when it comes picks the job up.

The lab behind it: durable sleep preserves an intention

This program is an Engineering Lab: beside the how-to it prints the rows that show what happened, and its notes weigh the design against the alternatives.

The problem

A process-local delay preserves a continuation only while that process lives. Long delays also tie the design to one in-memory execution even though no useful work is happening.

Common approaches

  • Task.Delay or PeriodicTimer inside a live process.
  • Self-reschedule and re-check readiness in the handler.
  • Persist a named durable timer checkpoint.
  • Let an external scheduler enqueue future work.

Why this design

SleepAsync stores the due instant, re-arms the job for the future, clears its worker lease, and ends the execution. When due, the handler re-enters and the elapsed named timer lets it continue.

Trade-offs

Re-entry starts at the top; bare code before the sleep runs again. Wake-up precision is bounded by the database clock and worker polling/wakeup behavior, and every timer adds durable rows and scheduling work. Code after the sleep can also repeat if the process dies after its external side effect but before job completion. Durable sleep preserves a due intention; it does not make later delivery exactly once.

Break it

Run a real process boundary against one configured database:

start persists a fifteen-second timer and exits. inspect starts no worker and proves the same job is still stored without a lease. recover enqueues nothing: it starts a worker and waits for that exact identity to re-enter and finish. Contrast this with Task.Delay, whose process-local continuation would have disappeared.

When not to use

Use Task.Delay for short process-local pacing that need not survive restart. Use an external scheduler when another system owns the timing. Self-reschedule is clearer when each wake must re-check a changing condition rather than merely wait for an instant.
