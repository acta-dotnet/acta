# Acta certification seal

**Verdict: PASS** — **1,000,000 jobs** on SQL Server, all eight checks green, zero failures. Provider
parity at scale: the same million-job shape that passed on PostgreSQL earlier the same day, on a
different engine with different locking, isolation, and routine dialect.

| | |
|---|---|
| Captured | 2026-08-12T13:00:35Z |
| Provider | SQL Server 2019 (15.0.4470.1, Developer Edition) |
| Schema | `acta_cert_mssql1mc` |
| Workload | Anvil `CrashRecovery`, **1,000,000 jobs**, 40 worker processes × 64 executors = **2,560 concurrent slots**, 5 durable steps each at 500ms |
| Chaos | Real `Process.Kill` every 5s for an 18-minute window |
| Quiesce | Chaos stopped, then waited until every job this run seeded (by correlation key) reached a terminal status |
| Wall clock | 57m 26s from first worker registration to verdict |

**Timing — framework production defaults, unmodified**: `LeaseTtlSeconds` 180, `HeartbeatInterval`
45s, `WorkerDeadAfter` 5min, `SafetyPollInterval` 1s.

**One deliberate difference from the PostgreSQL seal**: the step body sleeps 500ms rather than 1000ms,
halving the job's wall-clock cost so a million of them finish in an hour on this engine. The step
count, the chaos cadence, and every timing default are identical. See *Throughput* for why that
change bought less than it looks like it should.

## Why this run has a clock note, and the first attempt did not have a seal

An earlier million-job attempt on this engine (`acta_cert_mssql1m`, preserved) **failed**
`step-replay` with 2,208 rows. Every one was a false positive. The check compared a step-body note's
timestamp against the step's `modified_at_utc` and read an inversion as a body running after its own
success. It was not: each of those jobs had `attempt_number = 1`, one execution, one worker, and
exactly one note per step.

The cause is that every routine captures its clock at entry — `@now = SYSUTCDATETIME()` before
`BEGIN TRANSACTION` — so a write that then blocks on locks lands with a stale stamp. Under this much
concurrency that stamp ran up to 30 seconds behind, far enough to produce 2,217 step rows whose
`modified_at_utc` preceded their own `created_at_utc`.

`step-replay` now counts instead of comparing: each body writes one note, `attempt_number` is how
many times the engine admitted a body, and **notes > attempts** is a body that ran unadmitted. Same
claim, no clock in it. Re-run against the failed run's preserved schema, it returns zero.

`clock-backsteps` is the new **measured** check: `events.id` is assigned in insert order, so a higher
id carrying an earlier timestamp counts a backwards write. It reports and never fails, because a
stale stamp from a blocked write and a container clock that genuinely stepped back are
indistinguishable from inside the database, and only one is a fault. This run recorded 42,707 — more
than the run that failed — which is the point: the property being certified never depended on the
clock, and now the seal shows that rather than the reader having to trust it.

## Throughput

Sustained **~280 jobs/s**. Notably, that is *not* concurrency-bound the way the PostgreSQL run was.
Going from 1,536 slots at 1000ms to 2,560 slots at 500ms — 67% more slots and half the sleep — bought
36%. If the sleep were the constraint, halving it would have doubled the rate.

The bottleneck is database round trips: roughly 20 per job (5 steps × start + note + complete, plus
claim, start, and complete), so ~280 jobs/s is ~5,700 round trips per second. PostgreSQL reached 267
jobs/s while each job took *twice* as long, which is the same statement about round-trip cost from
the other direction.

## Scope

Single namespace, single machine, one provider. Multi-namespace ensemble and tenant spread remain
unrun; those are the rest of the W2 gate. The checks are `anvil/Anvil/certify.sql` with the schema
token bound to this run's schema; re-run them against the schema to reproduce the verdict.
