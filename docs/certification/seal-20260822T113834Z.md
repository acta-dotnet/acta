## The burn, and why this provider had it too

SQLite assigns the AUTOINCREMENT rowid and advances `sqlite_sequence` *before* the conflict is
detected, which is the same ordering that made PostgreSQL burn an id on every worker start. Its
registration was therefore restructured alongside PostgreSQL's into the guarded shape SQL Server always
had. This gate is that change under 78 real registration calls, and the previous round's database file
still exists as the control:

| | Previous round (`acta-local-certrc1sq.db`) | This run (`acta-local-certrc1bsq.db`) |
|---|---|---|
| Worker starts (`start_worker` calls) | 78 | 78 |
| Namespace rows / highest id | 2 / 2 | 2 / 2 |
| **Allocator position (`sqlite_sequence`)** | **79** | **2** |
| **Ids burned** | **77** | **0** |
| Holes between lowest and highest id | 0 | 0 |

The identical start count on both sides is what makes this the round's cleanest reading: no scheduling
luck to discount, no difference in how hard the chaos hit, just the routine. Both files remain on disk
and either number can be re-read to reproduce it.

## Also still holding: the defect the 0.9.0 SQLite gate caught

`expected-outcome` is the check that failed on this provider before `v0.9.0-beta.1`, when one
`slow-success` job in fifteen thousand landed terminal Failed with no reason recorded because the
executor's ownership-lost path set a null failure reason. It reports zero rows here, and nothing in
this database terminalized Failed at all — 15,000 of 15,000 seeded jobs reached `Succeeded`.

version is this round's ensemble seal.

## Scope — reduced, and stated on its face

- **Single machine is the engine's deployment model, not a shortcut**: SQLite is embedded, so every
  worker shares the database file by construction. Kills, leases, reclaim, and multi-*process* claim
  contention are fully exercised; multi-*machine* topology claims are out of scope on this provider
  permanently, not merely untested.
- **One namespace, one participant**: `namespace-isolation` passes but cannot fail with a single live
  namespace in the database; the 3-participant / 2-namespace ensemble seal covers that (on a server
  engine — the ensemble shape presumes independent participant processes joining one database, which is
  the server providers' deployment model).
- Concurrency is 48 slots against the server engines' 64: the single write lock makes more executors
  contention rather than throughput; the run certifies the shipped SQLite guidance (`Direct` profile,
  WAL), not a server-class concurrency envelope.
- The burn measurement above is a two-namespace reading. Because the ids here are 1 and 2, the burn
  showed only in the sequence and left no holes in the table; the shape where it left visible holes is
  this round's ensemble seal, which created its second namespace after worker starts had begun.
