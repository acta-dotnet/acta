## The burn, where it was actually visible

Every gate in the previous round burned a namespace id per worker respawn, but only this shape shows it
in the table rather than only in the sequence — because only this shape registers a **second** namespace
after worker starts have already begun. The previous round's schema is the control:

| | Previous round (`certrc1ens`) | This run (`certrc1bens`) |
|---|---|---|
| Worker starts (`start_worker` calls) | 229 | 229 |
| Real namespaces (plus `sys`) | 2 | 2 |
| Ids actually assigned | `sys`=1, `cert-a`=2, **`cert-b`=10** | `sys`=1, `cert-a`=2, **`cert-b`=3** |
| **Holes between lowest and highest id** | **7** | **0** |
| **Allocator position after the run** | **230** | **3** |
| **Ids burned** | **227** | **0** |

In the previous round `cert-b` was handed id **10**: seven ids had already been burned by respawns in
the interval between the two namespaces registering. That is the density property stated exactly — a
burned id is an id with no row behind it — and it is why the fix's spec asserts density rather than an
allocator reading. On the certified tree, three participants respawning workers independently for seven
minutes leave the three namespaces at ids 1, 2, 3 with the allocator stopped at 3.

## Namespace isolation, falsifiable and held again

`cert-b` was not an empty row: it registered 76 workers, ran its recurring system slots plus Anvil's
pulse, recorded its own execution events (25 of them, beside `cert-a`'s 14,046), and had 56 of its
workers reclaimed dead, all while every participant killed workers every five seconds. The check
compares each execution event's namespace against its owning job's across the whole schema: **zero
rows**. No worker in either namespace ever emitted an event for work it did not own, under contention
that included a second live namespace to get wrong — and, this round, a second namespace whose id is no
longer where the burn would have put it.

`p2` joined the seeder's run thirty-four seconds after it started, claimed from the same queue for the
whole chaos window, and exited cleanly with code 0 once the run's work went terminal, having correctly
declined to render a verdict it does not own. `p3` holds no seeded workload — only `cert-b`'s five
recurring slots — so it has nothing to quiesce on and was stopped after the seeder's verdict.

## The double-spend claim, non-vacuous this time

The three single-participant runs of this round all reported `at-most-once = 0` with zero interrupted
charges — vacuously true. Here the kills landed: of 400 charges, **43 were interrupted mid-body** and
terminalized as ambiguous rather than re-run, 357 succeeded, and every one of the 400 wrote exactly one
witness note — **no charge body ever ran twice** (maximum bodies per job: 1; jobs with two or more
bodies: 0). That is the contract stated exactly: zero or one executions, never two, with an honest
"this may have happened once" instead of a confident second charge.

## Scope

Single machine, three processes; the participants are process-isolated, not network-isolated. `cert-b`
carried recurring work rather than a second seeded workload — enough to make isolation falsifiable, not
a throughput claim for two namespaces at once. Only a namespace's seeder stages outbox rows, so
`cert-b`'s relay drained an empty, pre-provisioned producer file and the outbox evidence in this seal
belongs to `cert-a`. Orphaned attempts carry no `worker_id` — they are written by `sys.recovery` as a
system actor — so reclaims are attributed per participant through `worker.died` and the worker row, not
through the orphaned attempt itself. The checks are `anvil/Anvil/certify.sql` with the schema token
bound to `certrc1bens`.
