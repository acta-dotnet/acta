## The negative control

SQL Server never burned. Its registration has always been a guarded `INSERT ... WHERE NOT EXISTS`, and
that is precisely the shape the fix gave PostgreSQL and SQLite. So its allocator reading is expected to
be unchanged, and it is:

| | Previous round | This run |
|---|---|---|
| Worker starts (`start_worker` calls) | 80 | 80 |
| Namespace rows / highest id | 2 / 2 | 2 / 2 |
| **Allocator position (`IDENT_CURRENT`)** | **2** | **2** |
| **Ids burned** | **0** | **0** |
| Holes between lowest and highest id | 0 | 0 |

This is worth as much as the two fixed providers' numbers. Eighty worker starts leaving the allocator
at 2 on an engine that never had the defect is what establishes that PostgreSQL's 81 → 2 and SQLite's
79 → 2 are the fix working, rather than a change in how the allocator is being read. `namespaces.id`
reads as `int` (precision 10) in `information_schema.columns`.
