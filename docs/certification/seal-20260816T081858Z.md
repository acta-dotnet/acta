## Why the round was re-cut

A seal certifies a commit, not a week. PostgreSQL and SQL Server had already passed on `080c790`
the same morning, and those passes were real — but the SQLite gate that followed them failed
`expected-outcome` on one row, the fix changed executor behaviour on every provider, and a seal
that quoted a tree the tag will not carry would be worth nothing. So all four gates were re-run on
`8f03356`, from empty schemas, at the same sizes. The earlier passes stand as validation of the
harness and the workload; the four seals of this round are the ones that certify the release. The
SQLite seal of this round (`seal-20260816T085003Z.md`) records what its gate caught and what
changed.

The outbox split-check design — the staging table lives in the producer's database, so *drained*
and *delivered* are Anvil's to prove and `outbox-relayed-outcome` is the ledger's — is described in
the PostgreSQL seal of the previous round (`seal-20260815T020214Z.md`). It is unchanged here, and
certified again under the same chaos: the 5,000 rows were staged in small committed batches spread
across the whole kill window, so relay claims raced worker kills the entire time.

**The re-run reproduced the previous round to within scheduling luck**: 579 orphaned attempts
against that seal's 584, 73 workers reclaimed dead against 73, identical job, step, and receipt
totals to the row. The executor change is a different answer on a path this run never took —
nothing here moved because of it, which is exactly what a fix to a rare branch should look like on
the engine that never hit it.

**Stated plainly:** zero charges were interrupted mid-body this run, so `at-most-once = 0` is
vacuous here — no kill happened to land inside a charge body among the 579 orphaned attempts. The
non-vacuous version of that claim is this round's ensemble seal (`seal-20260816T090216Z.md`), which
interrupted 44.
