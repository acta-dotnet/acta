**Verdict: PASS (reduced scope)** — every asserted property held, the chaos was real, and this run
proves the step claim that the previous seal could not observe.

Read the scope section before quoting this. It is a real result on a real run, and it is narrower
than a full certification.

**Timing configuration — framework production defaults, unmodified.** Anvil overrides
`ExecutionProfile`, `MaxConcurrentExecutors`, `ClaimBatchSize` and `DeploymentVersion` only; the
timing triad is untouched (`Program.cs:160` states this deliberately).

| Setting | This run | Default |
|---|---|---|
| `LeaseTtlSeconds` | 180 | 180 |
| `HeartbeatInterval` | 45s | 45s |
| `WorkerDeadAfter` | 5min | 5min |
| `SafetyPollInterval` | 1s | 1s |

**This table is not decoration: every property below is timing-dependent.** A shorter lease
manufactures more handler overlap than production would ever see, by reclaiming live-but-slow workers
more aggressively; a longer one hides overlap that production does see. A seal produced with
non-default timings certifies *that configuration*, not the shipped one, and must say so here.

It also explains the gap between two numbers in this run: reclaim fires on the **180s lease**, while
`worker.dead` waits for **5 minutes** of heartbeat silence (`WorkerDeadAfter`). Different windows, so
orphan counts lead dead-worker counts throughout — which is exactly why check 8 keys on orphans.

## The number

| | |
|---|---|
| Attempts started | 1,155 |
| Jobs succeeded | 1,000 (all of them) |
| Steps recorded | 5,000 |
| Step-body notes | 5,147 |
| Attempts orphaned by killed workers | 147 |
| Worker rows created (target 6) | 50 |
| Workers marked dead by recovery | 44 |

**5,147 − 5,000 = 147.** Step-body notes minus recorded steps equals the orphan count, exactly.

Each killed worker caused precisely **one** step body to re-run — the one in flight when it died —
and no already-recorded step re-ran. That is "kill the worker, completed steps do not re-run" as
arithmetic rather than assertion, and check 7 independently confirms the sharper form: **no body ran
after its step had already succeeded.**

This was unobservable in the previous seal. `steps` keeps one row per `(JobId, Name)`,
UPDATE-in-place, with no per-attempt history, so a body that ran twice left no trace anywhere. The
`ctx.NoteAsync` witness is what made it measurable.

## Scope — what this does NOT say

- **Not "lease exclusivity".** Check 1 is *execution-event ownership consistency*: no two workers
  emitted execution events for the same attempt. It cannot see a claim that died before emitting
  `job.execution-started`, nor two overlapping claims carrying different execution numbers.
- **No handler-body overlap and no `AtMostOnce()` double-spend.** Overlap needs enter/exit notes plus
  an external kill record carrying the killer's timestamp; `AtMostOnce()` needs its own probe.
  Neither exists yet.
- **Single host, single namespace, no tenants, no outbox.**
- **1,000 jobs on one provider.** SQL Server and SQLite were not certified here.

## Sizing, learned the hard way

`JobsOptions.LeaseTtlSeconds` defaults to **180** and `sys.recovery` fires once a minute, so a killed
worker's job is not reclaimable for up to ~4 minutes. **Size a run by duration against that floor,
never by job count.** This run had *zero* orphans until its final minutes; an earlier 1,000-job
attempt drained in ~3.5 minutes and would have reported zero reclaims — INCONCLUSIVE, not PASS.

The same floor bounds quiesce: stopping the chaos does not end it, because jobs held by
already-killed workers stay `Executing` until their lease lapses. Wait for in-flight to reach zero,
not for the producer to stop.
