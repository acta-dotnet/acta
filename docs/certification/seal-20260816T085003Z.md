# Acta certification seal

**Verdict: PASS** — the SQLite run on the release commit, and the seal this release is proudest of:
the *first* SQLite run of this round failed, on one row out of fifteen thousand, and the row was a
real product bug rather than harness noise. It is the first time a certification gate has caught a
defect before a tag. The fix is `8f03356`; this PASS is the re-run against it, same six processes
on one WAL-mode database file, same kill cadence, same shape.

## The gate did its job

The first SQLite run of this round — schema `cert09sqb`, run `r20260816-053928-3c6819`, on commit
`080c790`, the same 10,000 jobs under the same 7-minute kill window (576 orphaned attempts, 72
workers reclaimed dead) — returned:

```
  [FAIL] expected-outcome             1 row(s)
```

One row. Job `2252`, a `slow-success` job with nothing exotic about it, sat terminal **Failed** at
`execution_number` 1 with `failure_count` **0**, no result row, and no failure reason recorded
anywhere. `expected-outcome` exempts the two definitions designed to fail; a plain `slow-success`
landing Failed is precisely the thing it exists to catch, and nothing else in the run was wrong.

**The signal that killed it was spurious, and the ledger proves that by elimination.** The story
the code told itself was that another execution had re-claimed the job — a step completion CAS
matching no row usually means exactly that, and `RuntimeJobContext` raises
`StepOwnershipLostException` on it. But `runtimes.execution_number` is incremented atomically on
every claim, and for this job it never left 1. The events agree: one `40`, one `41`, both carrying
execution 1, its tenant witness note and its `step-body step-1` note between them, and `steps`
holding a single row, `step-1`, Succeeded on attempt 1. There was no competing execution to have
bumped the version, so ownership was never lost — and the final proof is the terminal write itself,
which the completion CAS *accepted*: the row was still leased to the very worker that had just
concluded it no longer owned it. The one thing certain is the conclusion was false.

*Why* the CAS reported zero changes is a hypothesis, and this seal leaves it as one. The leading
candidate is a transient retry re-running a batch whose first attempt had already committed: the
re-run legitimately changes no rows and is indistinguishable, at `CHANGES()`, from a genuinely
stale version — which fits the standing `Microsoft.Data.Sqlite` transient watch item and fits an
attempt that ended some 1.04 seconds after its step body's note, right as step-1's one-second delay
elapsed. It is not proven, and the fix does not depend on it.

**What was actually broken was the answer, not the question.** The executor's ownership-lost path
set the outcome to Failed with *no* reason; a null reason is not retryable, so the non-retryable
terminal branch ran, and the completion CAS — which the worker still satisfied — wrote it. A
healthy job died silently, and only because the harness asserts on outcome did anyone see it.

On `8f03356` that path submits a **retryable** `job.attempt-aborted` failure with a message
instead. The two cases now separate themselves without the code having to tell them apart: a row
another execution really owns no-ops at the completion CAS exactly as it did before, while a row
this worker still owns re-arms under the failure budget and retries, replaying its recorded steps.
This run is that fix under identical chaos — 573 orphaned attempts against the failing run's 576,
72 workers reclaimed dead against 72 — with `expected-outcome` back to zero rows.

**Three engines, one ledger behaviour.** 573 orphaned attempts against PostgreSQL's 579 and SQL
Server's 574; 72 workers reclaimed dead against 73 and 72; identical job, step, and receipt totals
to the row on all three. Zero clock backsteps again — the embedded engine writes with no server
round trip to block on, which remains the cleanest illustration that the backsteps note measures
lock-wait patterns rather than correctness.

**Stated plainly:** zero charges were interrupted mid-body this run (as on both server engines this
morning), so `at-most-once = 0` is vacuous here; the non-vacuous version is this round's ensemble
seal (`seal-20260816T090216Z.md`).

## Scope — reduced, and stated on its face

- **Single machine is the engine's deployment model, not a shortcut**: SQLite is embedded, so every
  worker shares the database file by construction. Kills, leases, reclaim, and multi-*process*
  claim contention are fully exercised; multi-*machine* topology claims are out of scope on this
  provider permanently, not merely untested.
- **One namespace, one participant**: `namespace-isolation` passes but cannot fail with a single
  namespace in the schema; the 3-participant / 2-namespace ensemble seal covers that (on a server
  engine — the ensemble shape presumes independent participant processes joining one database,
  which is the server providers' deployment model).
- Concurrency is 48 slots against the server engines' 64: the single write lock makes more
  executors contention rather than throughput; the run certifies the shipped SQLite guidance
  (`Direct` profile, WAL), not a server-class concurrency envelope.
- **The fix carries no direct unit pin** — no executor harness exists to drive that catch in
  isolation, which is recorded as a post-release item. This run, and the failing run it answers,
  are the evidence the change has: one occurrence per ten thousand jobs under kill-every-5s chaos,
  reproduced as a failure before the fix and absent after it at the same shape.

`acta-local-cert09sqc.db` to reproduce the verdict.
