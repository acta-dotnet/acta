# Release notes

## 1.0.0-rc.10

Not tagged yet.

### What a consumer must change

**Drop and reprovision every database an rc.9 build provisioned**: the baseline is re-cut, and nothing translates it.

**Hold an execution number or a version in a `long`**: `JobContext.ExecutionNumber`, every execution number and version a response answers, and every version a control verb takes, `expectedVersion` among them, are 64-bit, and the OpenAPI document declares them `int64`. A job row's execution number and version are `bigint` on PostgreSQL and SQL Server, so a long-lived job no longer wears them out.

**Write an interval schedule in days or less**: `"P1M"` and `"P1Y"` were read as 30 and 365 days, and are now a build error (ACTA0122). Write `"P30D"` for thirty days, or a cron for a calendar month or year.

**Call `ResetStateAsync` as a handler's last action, not in a `finally` or `catch` around a wait or sleep**: there it deleted the checkpoint the job was suspending on, and it now throws once a wait or sleep has suspended the attempt.

**Catch `StepExhaustedException` around a step whose result may be too large**: `RunStepAsync` threw `PayloadTooLargeException` for a result over `MaxInlinePayloadBytes` and `InvalidOperationException` for a null one, and now throws `StepExhaustedException` for both.

**Stop reading `schedules.misfire_grace_seconds`**: the column is gone. Every row held the same sixty seconds, which is the engine's own constant now, so a query that named the column drops it.

**Read a step's failure from its status**: `steps.failure_code`, the `failure` and `failure_code` columns of `steps_view`, `StepFailureCode`, and `StepExhaustedException.LastReasonCode` with its constructor argument are gone. `Exhausted` always meant the body threw and `Interrupted` always meant the step was re-entered before it completed, so the code restated the status. `failure_message` and `LastReasonMessage` keep the reason.

**Read whether the engine or a handler raised an alert from its kind**: `alerts.alert_origin_code`, the `alert_origin` and `alert_origin_code` columns of `alerts_view`, `AlertOriginCode`, and the `origin` field of the alert responses are gone. The kind `manual` is a handler's alert and every other kind is the engine's, so the origin restated the kind.

**Stop reading or filtering on a schedule's origin**: `schedules.schedule_origin_code`, the `schedule_origin` and `schedule_origin_code` columns of `schedules_view`, `ScheduleOriginCode`, the `origin` field of the schedule responses, and the `origin` filter of the schedule list (`ListSchedulesQuery.Origin` and `origin` on `GET /schedules`) are gone. Every schedule comes from a `[Schedule]` declaration, so the origin was always `definition`.

**Read who performed an operator action from `events.actor`, not from `details`**: an operator verb's event names its operator in the `actor` column, which `events_view` shows beside `event_message` and an event over HTTP carries as `actor`, and `ListEventsItem` gains `Actor` after `Message`. The `actor` fact of `details` no longer exists: `details` holds only machine-readable facts, so a verb whose only fact was its operator now writes no details. A handler's state reset names its job's id as the actor, as its details did.

**Catch `EnqueueRejectedException` for a child whose parent is gone**: an enqueue that names a `ParentJobId` of a job that does not exist or has finished threw the database provider's own exception, and now throws `EnqueueRejectedException` with the reason `ParentUnavailable`, as every other refused enqueue does. The HTTP enqueue takes no parent, so its answers are unchanged. A child a handler starts after its attempt lost the job still throws `ExecutionFencedException`.

**Stop reading `quarantined=` in an outbox source's last tick**: the `lastTickSummary` of `GET /outbox/sources` and the `sys.outbox` job's `outbox-status` variable no longer carry the number of rows the pass quarantined. It was zero in every stored summary, because a pass that quarantines a row fails and stores none. `quarantineTotal` is the count to read.

**Recreate the outbox table, or rename five of its columns**: `job_namespace` is `namespace_name`, `lane` is `lane_name`, `priority_code` is `job_priority_code`, `status_code` is `outbox_status_code`, and `last_error` is `failure_message`, so the table names its columns as every Acta table does. Create it again from the provider's `CreateOutboxScript`, or rename the columns in place, and change any SQL of your own that reads the table, such as a cleanup job or a monitoring query. Staging through `AddToActaOutboxAsync` needs no change, and no constraint or index is renamed.

### Fixes

- On SQL Server, two definition overrides updates in different namespaces could deadlock, and one failed as the victim: the update that carries a rate override to the definitions sharing its meter read every definition row under update locks before filtering by namespace, and waited on another namespace's row that its own update held. It now seeks its own namespace's rows.
- On SQL Server, a definition overrides update read every job row under update locks to find the definition's permanent job, so it waited on any other namespace's open work. It now seeks the definition's permanent job.
- On SQL Server with READ_COMMITTED_SNAPSHOT off, a job purge, the jobs listing, and the events listing read every row of `events`, `lanes`, or `workers` respectively, so each waited on another namespace's open transaction. Each now reads only the rows it joins.
- On SQL Server, retiring a definition read every schedule row under update locks, so it waited on any other namespace's open work. It now seeks the definition's schedules. With READ_COMMITTED_SNAPSHOT off, a schedule's trigger, pause, and resume, and the definitions listing, likewise waited on another namespace's open work; they now read only their own rows.
- On SQL Server, the worker heartbeat renewed its concurrency slots and named locks by reading every row of `locks` under update locks, so it waited on another namespace's open work. It now seeks the locks it holds.
- On SQL Server, the crash-recovery pass applied the firing failure policy by reading every schedule row under update locks, so it waited on another namespace's open work. It now seeks the definition's schedules, and a recurring job's completion, which runs the same update, seeks them too.
- On SQL Server, the retention sweep deleted an expired job's tags by reading every job tag under update locks. It now seeks each job's tags.
- On SQL Server with READ_COMMITTED_SNAPSHOT off, alert delivery, a job lookup by deduplication key, a schedule read, the tags listing, and the calendar reads (a calendar, one of its versions, the listing, an archive, and the published calendars that admission and deploy load) each read other namespaces' rows and waited on their open transactions. Each now seeks its own namespace's rows. The overview now reads its alert and worker counts without locks, as it already read its job and schedule counts.
- A calendar listing counts a shared calendar's dependents as that calendar's dependents list reads them, skipping a schedule another transaction holds.
- A `[Job]` method with a `ref`, `out`, `in`, or `ref readonly` parameter passed the generator, which calls the handler with by-value arguments, so a by-value overload of the same name ran in its place and its result was stored as the job's. A second `CancellationToken` likewise passed, and the call supplied one token. Each is now ACTA0103, and a second `JobContext` names itself rather than reporting a parameter order.
- On PostgreSQL, the crash-recovery pass could read a stuck job's lanes through `ix_jobs_state_lane_member`, every live laned row, when the table's statistics priced it the same as `ix_jobs_state_worker_inflight`. It now reads them through the in-flight index alone.
- A `RunWithLockAsync` action or a concurrency-limited handler could run while another attempt held the same lock. A hold whose acquire was answered late was trusted for a full lease, though its lease had started at the request, and when one worker process ran a stale and a current hold on one key, the heartbeat's renewal of the current hold kept both attempts running. Each hold now has its own deadline from its acquire's request, an action whose hold is already past it does not start, and the heartbeat matches a renewed hold by its token.
- A cancel's descendant walk could cancel a child the job started after a restart. The walk runs after the cancel commits and repeats after a database error, so a restart and a new execution could come in between, and the walk cancelled whatever children the job had by then. Each cancel in a walk now lands only while the walked job is still Cancelled, and the walk ends at the first that finds it restarted.
- On PostgreSQL, a batch enqueue that waited on a lane or a parent while one of its namespaces was suspended committed the other rows and then threw, so a retry without deduplication keys enqueued those rows twice: the staging dropped the rows of a namespace whose status changed after the batch's check. A batch that passed the check now lands whole.
- On PostgreSQL and SQL Server, a batch enqueue naming a tenant that was suspended or resumed at the same moment could store its jobs without that tenant, or with the parent's: the tenant was resolved only while Active, a statement apart from its check. A named tenant now resolves by name, the checks judge the tenant it resolved to, and a child takes its parent's tenant only when it names none.
- A schedule with `ExpireAction = Pause`, parked as `waiting-for-capacity` on an occurrence that had not aged past its expiry yet, had no wake of its own, so while the slot stayed busy the occurrence never expired and the schedule never paused. It now wakes when the waiting occurrence expires and pauses then. A `Discard` expiry still decides the aged occurrences as one range when the slot frees.
- A schedule more than a million occurrences behind stopped for good: the evaluation gave up, kept the cursor, and gave up again on every pass, so a cron with seconds left unevaluated for twelve days, or the five-second `sys.outbox` schedule after fifty-eight days of a stopped environment, a suspended namespace, or a pause, never fired again. A backlog is now searched instead of walked past its first thousand occurrences, so its depth no longer matters, and a cron whose zone skipped a calendar day is refused as an evaluation error at once instead of after a million steps.
- A schedule whose expression kind or misfire strategy a newer build stored stopped every older worker's admission pass for its whole namespace, and one whose status it could not read was put to sleep by it. A schedule that holds a code the build does not know (status, kind, strategy, full behavior, expire action) is now left out of that build's due list and wake horizon: its admitter leaves the row alone and every other schedule in the namespace keeps firing. After a rollback, `jobs deploy --force` from the older build puts its own declaration back. A calendar publication from the older build leaves such a schedule as it is too, where it used to retime it.
- Retention's job sweep read a fixed stretch of the whole jobs table each hour, whatever namespace the rows belonged to, so on a large table an expired job waited hours or days for the walk to reach it, and under a steady high load the walk never caught up. Each namespace now walks only its own jobs, starting at the newest one old enough to have expired, and a pass that deleted jobs and has more to walk runs again at once.
- On PostgreSQL a child enqueued from outside its parent's handler while the parent was being cancelled could be stored under the cancelled parent after the cancel had walked its children, and then ran. The enqueue now reads the parent again once it holds its row, and is refused.
- A job enqueued through the SQL `enqueue_job` routine with a key the API refuses, such as one holding a space, could not be claimed: the claim failed on reading its key, and with it every job claimed beside it, and reading or listing the job threw; one with such a concurrency key was put back every few seconds and never ran. A stored key is now taken as stored by the claim, the concurrency slot, and the reads. The routine also stored a priority that is not a band, which no claim ever reads, and an empty or blank key, which every later enqueue then shared; it now refuses both, and a definition's priority override is held to the bands as well.
- Retention deleted a finished job whatever its alerts said, so an alert outlived its job: an undelivered one then named a job nobody could open, and a manual purge and retention disagreed about which rows a job owns. Retention now keeps a job while one of its alerts is undelivered and deletes its settled alerts with it.
- A failure event whose job was gone left a skip record that no pass could ever clear, and that record held the event retention floor at it for good. Such an event is now passed with no record, and a record already stored for one is dropped by the next pass.
- Two fan-out groups could start one child between them. A group's children were named `{group}-{item}`, so group `ship` with branch `eu-west` and group `ship-eu` with branch `west` both asked for `ship-eu-west`, as did a child named so by hand, and the second start deduplicated onto the first. A group's children are now keyed `{group}/{item}`, which no name can spell.
- A worker's declared namespace description was refused past 256 characters, half of what the column and the namespace update accept. The build now takes the same 512.
- One alert endpoint that never answered held every other channel: a send had no limit, and a pass sends its alerts one after another, so the alerts behind a hung webhook waited until the pass timed out, on every pass. A send now has ten seconds, enforced on the wait as well as through its token, which is cancelled at the limit whether or not the send has returned its task, a channel that misses it is not asked again in that pass, and a pass that has spent thirty seconds leaves the rest for the next one.
- A deploy that dropped a schedule left no event, and one that changed a schedule's timing recorded it only at `Audit`, so on a quiet definition a schedule could stop or move with nothing to show which release did it. A dropped schedule now records `schedule.orphaned`, and a retimed one, or one a deploy declares again, records `schedule.retimed`, each at every recording level.
- A worker marked dead through a database outage came back to `Active` on its next heartbeat with no event, so its timeline ended at `worker.died` while it went on running jobs. The heartbeat that revives it now records `worker.started`.
- A deploy cleared the owner team or description an operator had set on a namespace whenever the build did not declare one, so the edit lasted until the next release. A value the build declares is still rewritten by every deploy; one it does not declare is now left as the operator set it.
- An exception that is never retried (`NotSupportedException`, `NotImplementedException`, an uncaught `StepExhaustedException`, a handler DI cannot build) stopped a permanent job for good: its slot landed Failed and every later occurrence was held until an operator restarted it, the sys jobs included. The firing now fails at once and the job returns to Idle for its next occurrence, as a spent budget does and as the developer guide already said; `FiringFailurePolicy` applies as for any firing that fails for good. A handler's own `FailAsync` still stops the job.
- A firing that failed for good after its definition was retired still applied `FiringFailurePolicy = PauseScheduling`, pausing the retired definition's schedules. The pause outlived the retire: a redeploy brought the schedules back paused, and they never fired until someone resumed them. The policy now leaves a retired definition alone.
- What changes a schedule's standing left no event on a job recorded below `Audit`: the firing failure policy's pause, an expiry's pause, a timed pause that ends, and a manual trigger. Every sys job records at `Failures`, so the engine could stop one's schedule without a trace. Each is now written at every recording level; an admission and a skipped range are per-occurrence decisions and stay at `Audit`.
- A result that could not be recorded ran its body again. A handler, or an ordinary step, that finished and returned null, a value that would not serialize, or, for a step, a value over `MaxInlinePayloadBytes`, failed the attempt as any exception does, so the retry ran the finished body a second time. Such a step now throws `StepExhaustedException`, which a handler can catch to compensate and which fails the job for good when uncaught; such a handler result fails the job for good. Either way the budget is untouched. An operator restart runs an ordinary step again and finds an at-most-once one interrupted. An oversized handler result is still dropped with the job succeeding.
- A control verb left no event on a job recorded below `Audit`: a pause, resume, restart, reschedule, priority change, input update or cancel changed what ran and nothing said who did it or why. Each now writes its event at every recording level. A cancel that reaches a job from an ancestor, by the ancestor's own cancel or by a child wait that timed out, and a raised signal are still recorded only at `Audit`.
- A suspended job was woken by any signal raised to it, and a parent by any of its children landing, whether or not that was what it waited on: it ran, found its wait unsatisfied, and suspended again, so a parent joining N children ran about N times. Only the signal or child a job waits on releases it now; anything else is recorded for the wait that will read it.
- A parent that had already finished never learned what its child did afterwards. A child that landed later, or that an operator restarted or cancelled, left the old outcome (or none) on the parent, and a restart of the parent replayed its wait against that stale outcome. A child's outcome is now recorded on its parent whatever the parent's status; a finished parent is not woken by it.
- A schedule descriptor built by hand could deploy and then never fire: a kind, misfire strategy, full behavior, or expire action outside its family is stored as a code no admission pass lists, an interval that does not parse threw a bare error during registration, and a zone was checked only on a cron although a schedule held to an availability calendar reads it too. The deploy now refuses each of these before it writes anything, naming the job and the schedule. Generated manifests were never affected.
- SQL Server: a manual trigger of a per-occurrence schedule by an operator whose name holds a character outside ASCII stored an event whose details were not valid UTF-8, in a database with the usual Latin collation, and reading that event failed. The details are stored as UTF-8 now.
- A schedule whose next occurrence cannot be computed (an unknown time zone, a calendar this build cannot read, a calendar that throws) stopped admitting with only a worker log line to say why. It now also writes one `schedule.evaluation-failed` event when the failure starts, with the error as its message, at every recording level, and the schedule's page in the dashboard shows it. A schedule in error stays in error while its source still fails, whatever its job is doing.
- A handler that ignored its cancellation token after its execution timeout held its job, its concurrency slot, and its locks with nothing said. It still holds them until it returns, since the body they guard is still running, but the worker now logs an error naming the job once the handler has run more than half a lease past its timeout. Known limitations says what that costs and how a restart frees the job.
- SQL Server: a job list filtered by lane across every namespace waited on an application's open laned enqueue into a new lane once `lanes` was large enough for the engine to lock pages for a scan. The lane probe takes row locks now and skips the uncommitted lane, as the list always promised.
- Under `Skip`, a timed schedule pause that ended while its permanent job was busy or unavailable, or while the schedule was full, could still fire an occurrence from inside the pause: the pass that ended the pause parked the schedule, and when the job freed within the minute of grace, the next pass saw an active schedule with an occurrence less than a minute old. The pause's window is now skipped at the pass that ends the pause, whatever the job or the schedule can take. The same held for a cursor that a changed calendar moved into the pause's window at that pass, and the pause now stays until the pass that decides it.
- A failed `sys.outbox`, `sys.alerts`, or `sys.retention` pass retried on a job's default curve, one minute doubling to a day, so after a few failures in a row the relay's five-second pickup, alert delivery, and retention waited minutes to hours behind one failed pass. The three jobs now retry after fifteen seconds, doubling to a minute, so three failures in a row, which raise the critical alert, come within a minute where they took three.
- A `union` availability calendar with an always-open week among its operands threw on every evaluation, preview, and deploy: it followed the week's touching windows until the date passed year 9999. A union now follows touching windows as far ahead as a weekly calendar scans, so a run that ends is answered whole, and up to a month back.

## 1.0.0-rc.9

Tagged 2026-11-09. rc.9 makes deploys explicit with `jobs deploy`, moves the dashboard into its own package, gives operations and the HTTP contract one naming convention, and runs on SQL Server with READ_COMMITTED_SNAPSHOT off as well as on. The schema changes: reprovision, as every pre-1.0 release asks.

### What a consumer must change

**Drop and reprovision every database an rc.8 build provisioned**: the baseline is re-cut, and nothing translates it.

**Enqueue options are written with the builder.** `IJobs.EnqueueAsync(input, JobEnqueueOptions? options)` and its transactional twin are gone, so the input form takes options the way the generated call does: `jobs.EnqueueAsync(input, new JobEnqueueOptions { DeduplicationKey = key })` becomes `jobs.EnqueueAsync(input, o => o.DeduplicationKey(key))`. `JobEnqueueOptions` stays as the value the builder builds, and a run-and-wait still takes its `JobExecutionOptions`.

**A typed run-and-wait goes through the job's call.** `IJobs.RunAndWaitAsync<TInput, TResult>(TInput input, ...)`, which needed both type arguments spelled out, is gone: `jobs.RunAndWaitAsync<ShipOrder, ShipmentLabel>(new ShipOrder(7))` becomes `jobs.RunAndWaitAsync(ShippingJobs.ShipOrder(new ShipOrder(7)))`, which answers the same `JobOutcome<ShipmentLabel>`. `RunAndWaitAsync(input)` without a result type stays.

**A scheduled definition's long-lived job is a permanent job, by every name.** Its job kind is `JobKindCode.Permanent`, code `permanent`, where it was `PermanentSlot` and `permanent-slot`: in the HTTP API's job `kind`, the jobs list filter, `jobs_view.job_kind`, and the CLI. A schedule whose occurrence waits on it while it is held, cancelled, or failed reads `job-unavailable` (`ScheduleEvaluationStatusCode.JobUnavailable`), where it was `slot-unavailable` (`SlotUnavailable`). The outbox source read names it `jobRef` (`ListOutboxSourcesItem.JobRef`), where it was `slotJobRef`.

**The operator views name their columns as the tables do, and only a decoded column gets a new name.** A view column is the table column's name (`namespace_name`, `definition_name`, `lane_name`), and a decoded label is the code column without `_code`: `job_status`, `job_priority`, `alert_kind`, `alert_origin`, `alert_severity`, `calendar_role`, `calendar_status`, `checkpoint_kind`, `checkpoint_status`, `definition_status`, `schedule_origin`, `schedule_status`, `step_status`, `worker_status`, and `entity` for the tagged or recorded entity's kind. `definitions_view` decodes its effective policies as `job_priority_effective`, `deadline_behavior_effective`, `event_recording_effective`, and `alert_profile_effective`. From 1.0 a view column is renamed or removed only in a major release.

**The outbox table's script moved to each provider's migrations class**: `PostgresOutboxDdl.CreateScript()`, `SqlServerOutboxDdl.CreateScript()`, and `SqliteOutboxDdl.CreateScript()` are `PostgresMigrations.CreateOutboxScript()`, `SqlServerMigrations.CreateOutboxScript()`, and `SqliteMigrations.CreateOutboxScript()`, with the same arguments and the same script.

**A step retries through its job.** A step body that throws fails the attempt: the job's `MaxAttempts`, `Backoff`, and Strict deadline retry it, and the retry replays the steps that succeeded and runs this one again. A step keeps no retry budget of its own, so `StepOptionsBuilder.MaxAttempts`, `Backoff`, `WithPolicy`, `BackoffInitialDelay`, `BackoffMaxDelay`, `BackoffMultiplier`, `BackoffJitter`, and `RetryWindow` are gone, with the matching `StepOptions` members: set the policy on the `[Job]` instead (`[Job("charge", MaxAttempts = 5, Backoff = "2s..1m")]`), and `AtMostOnce()` is the one step option.

- A wait, sleep, or child wait inside an ordinary step body works: the resume runs the body again up to the wait, which returns what it already has, and spends nothing. Inside an `AtMostOnce()` body it, and a reschedule or pause, throws `InvalidOperationException` at the call, before it writes anything, and a `RescheduleJobException` or `HandlerPauseException` the body throws itself exhausts the step the same way.
- `StepExhaustedException` is the failure of an `AtMostOnce()` body, which never runs again, and its `AttemptCount` and that constructor parameter are gone.
- `ctx.IsLastAttempt` is true when a retryable failure of this attempt would end the job for good, or a permanent job's current firing: the failures already charged leave no `MaxAttempts` budget for a retry, or the retry's backoff would land past a Strict deadline. It reads the budget, never the execution number, so a resume after a sleep or a wait leaves it false. A non-retryable exception ends the job on any attempt, so compensate with `catch (Exception ex) when (ctx.IsLastAttempt || ex is StepExhaustedException) { await ctx.RunStepAsync("release-stock", ...); throw; }`, best effort, since a crash on the last attempt skips the catch; see [Compensating on the last attempt](developer-guide.md#compensating-on-the-last-attempt).
- The step's attempt number and retry instant are gone from every surface: the `steps.attempt_number` and `steps.next_retry_at_utc` columns with the checks `ck_steps_attempt_number` and `ck_steps_terminal_no_retry`, the `attempt_number` and `next_retry_at_utc` columns of `steps_view`, `ListJobStepsItem.AttemptNumber` and `NextRetryAtUtc`, and `attemptNumber` and `nextRetryAtUtc` on `GET /jobs/{jobRef}/steps`. Removing a view column is a pre-1.0 change; from 1.0 only a major release removes one.
- `IActaTestHost.ForceStepRetryDueAsync` is gone, and no event carries the reason `step-retry-scheduled`.

**The test host's job helpers take a `JobLookup`, as `IJobs` does.** `IActaTestHost.RunOnceAsync`, `ForceJobDueAsync`, `ForceTimerDueAsync`, `ForceWaitTimeoutDueAsync`, `ForceGroupWaitTimeoutDueAsync`, and `ExpireExecutionLeaseAsync` take the job as a `JobLookup` where they took a `long` job id, and `RunOnceAsync(EnqueueJobResponse)` is that same one method. The enqueue's `JobHandle` or `EnqueueJobResponse` and a `JobRef` pass as they are, so a test drives a scheduled job by the ref `ISchedules.GetAsync` answers rather than resolving its id first; a call that passed an id passes `JobLookup.ById(id)`. A ref or deduplication key that matches no job throws `InvalidOperationException`.

**Operations follow one naming convention, and their public types follow them.** An operation is a verb and its subject, a facade method is that name without the facade's noun, and a part of an aggregate names the aggregate. The renames:

- `SetDefinitionOverridesResponse` is `UpdateDefinitionOverridesResponse`, as `IDefinitions.UpdateOverridesAsync` already said.
- `GetJobExplanationResponse` is `ExplainJobResponse`, as `IJobs.ExplainAsync` already said, and its parts `GetJobExplanationWait`, `GetJobExplanationLease`, `GetJobExplanationStep`, and `GetJobExplanationAction` are `ExplainJobWait`, `ExplainJobLease`, `ExplainJobStep`, and `ExplainJobAction`.
- `GetResultResponse` is `GetJobResultResponse`; `IJobs.GetResultAsync` keeps its name.
- `IJobs.GetCheckpointsAsync(job)` is `IJobs.ListCheckpointsAsync(new ListJobCheckpointsQuery(job))`, and `GetCheckpointsResponse` and `GetCheckpointsItem` are `ListJobCheckpointsResponse` and `ListJobCheckpointsItem`: it answers one page of the job's checkpoints by kind, then name, with `PageSize`, `Cursor`, and `IncludeTotal` as every list takes them, and an empty page rather than `null` for a missing job. `GET /jobs/{jobRef}/checkpoints` pages them over HTTP and answers 404 for an unknown job, and `GET /jobs/{jobRef}/detail` carries `checkpoints` as the first page (`items`, `nextCursor`, `hasMore`, `pageSize`, `totalCount`) instead of every checkpoint; in the OpenAPI document its items are `ListJobCheckpointsItem`, not `GetJobDetailCheckpoint`.
- `ITags.GetAsync(target)` is `ITags.ListAsync(new ListTagsQuery(target))`, and `GetTagsResponse` and `GetTagsItem` are `ListTagsResponse` and `ListTagsItem`: it answers one page of the target's tags by name in ordinal order, with `PageSize`, `Cursor`, and `IncludeTotal` as every list takes them, and an empty page rather than `null` for a target that does not exist. `GET /jobs/{jobRef}/tags`, `GET /namespaces/{jobNamespace}/tags`, `GET /tenants/{tenantName}/tags`, and `GET /definitions/{jobNamespace}/{jobName}/tags` answer that page (`items`, `nextCursor`, `hasMore`, `pageSize`, `totalCount`) and take `pageSize`, `cursor`, and `includeTotal`. Their outcomes are unchanged: 400 for a target that cannot be addressed, 404 for an unknown target, and 200 with an empty page for a target without tags.
- `GetCalendarResponse` no longer carries every version: `Versions` is replaced by `LatestVersion`, and `ShownStatus` is the status of `ShownVersion`. `ICalendars.ListVersionsAsync(new ListCalendarVersionsQuery(calendar))` answers one page of the family's versions, newest first, with `PageSize`, `Cursor`, and `IncludeTotal` as every list takes them, and an empty page for an unknown family; `GetCalendarVersion` is `ListCalendarVersionsItem`. `GET /calendars/{jobNamespace}/{calendarName}` answers `latestVersion` and `shownStatus` instead of `versions`, `GET /calendars/{jobNamespace}/{calendarName}/versions` pages the versions and answers 404 for an unknown family, and `GET /calendars/{jobNamespace}/{calendarName}/detail` answers the family with the first page of its versions (`calendar`, `versions`), which the dashboard's calendar page reads.
- `GetCalendarResponse` no longer carries the schedules that name the family: `Dependents` is gone, and `GetCalendarDependent` is `ListCalendarDependentsItem`. `ICalendars.ListDependentsAsync(new ListCalendarDependentsQuery(calendar))` answers one page of them, orphans included, by namespace, job, schedule, then binding, with `PageSize`, `Cursor`, and `IncludeTotal` as every list takes them, and an empty page for an unknown family. `GET /calendars/{jobNamespace}/{calendarName}` no longer answers `dependents`, `GET /calendars/{jobNamespace}/{calendarName}/dependents` pages them and answers 404 for an unknown family, and `GET /calendars/{jobNamespace}/{calendarName}/detail` carries their first page as `dependents`.
- `ExplainJobResponse.Steps` carries the job's newest 50 steps, and `StepsHasMore` says when older ones exist; `IJobs.ListStepsAsync` pages them all. The jobs CLI's `explain` says when it leaves older steps out, and its `--json` output carries `stepsHasMore`.
- `GetJobLineageMapResponse` carries the job's nearest 50 ancestors and newest 50 steps, with `AncestorsHasMore` and `StepsHasMore` beside `ChildrenHasMore`, and the dashboard's lineage map says when it leaves some out; `IJobs.ListStepsAsync` pages every step.
- `PreviewCalendarResponse.Schedules` lists at most 100 bound schedules, overdue ones first, and `SchedulesTotal` and `OverdueTotal` count them all; `ICalendars.ListDependentsAsync` pages every one. The dashboard's publish confirmation counts from the totals.
- `IJobs.GetJobIdAsync` is `IJobs.GetIdAsync`.
- `IJobs.UpdateJobInputAsync` is `IJobs.UpdateInputAsync`.

### Additions

- **A schedule can be finite.** `[Schedule("hourly", Cron.Hourly, StartAtUtc = "2027-12-01T00:00:00Z", EndBeforeUtc = "2028-01-01T00:00:00Z")]` bounds a schedule to the occurrences in [start, end), each bound a UTC instant written with a `Z` and either one optional; stored as `schedules.start_at_utc` and `schedules.end_before_utc` (`ck_schedules_bounds` holds the start earlier than the end), shown in `schedules_view`, and answered as `startAtUtc` and `endBeforeUtc` by `GET /schedules` and `GET /schedules/{jobNamespace}/{jobName}/{scheduleName}`, which the dashboard's schedule page shows as its bounds. The bounds are on the occurrences' own instants: the first is the first at or after the start, an interval with a start steps on the start's grid, and an occurrence before the end that is evaluated after it is decided by the misfire and expiry policies as any late one. Past the end the schedule reads `exhausted`; a build that extends the end retimes it, and declaring a bound on a running schedule retimes it too, discarding its undecided occurrences as any retime does. A trigger fires whatever the bounds. The generator reports `ACTA0129` for a bound that is not a UTC instant or a start not earlier than the end, and a worker refuses a hand-built descriptor with the same fault at start. The init migration is re-cut as `M20261108075926`.
- **A calendar deploy step runs again as it is.** A draft whose definition the family's latest version already holds, compared by content rather than layout, writes no version and no event and answers `already-in-state` (`ControlAction.AlreadyInState`) with that version, whatever expected version it sent; a definition an archived latest version holds saves a new draft. Publishing the version already current answers `already-in-state` too, and retimes nothing, records nothing, and is not refused for an overdue occurrence; of two publications of one draft at once, the second answers so. - **`<app> jobs migrate` applies Acta's migrations from a deploy step.** It runs the app with its own provider options, so it migrates the connection string and schema the workers use, prints each migration it applied or that the schema is up to date, then deploys the app's jobs as `jobs deploy` does, and exits 0 or 1. The Redis wakeup's line for a failed subscribe or publish escaped the wait and faulted the claim loop; the warning a database call writes while tearing down a failed attempt took that failure's place, so a deadlock it would have retried failed instead; and the worker host's warning for a stamp past its shutdown budget, or a loop that faulted while draining, ended the stop before it cancelled the worker's loops. Each now writes through a logger that ignores a sink's failure, as the worker's loops do.

### What a consumer must change

**Drop and reprovision every database an rc.7 build provisioned**: the baseline is re-cut (`M20261031153619_init`), and nothing translates it. **A retire leaves a recurring job's slot inert, and a newer build that registers the definition again resumes its schedules from now.** Before, a retire cancelled the permanent slot and cleared the schedules' cursors, and a reactivated definition kept both that way: its schedules never fired again. Now a retire settles a firing admitted and not yet claimed and returns the slot to `Idle`, keeps a paused or cancelled slot as the operator left it, returns the slot to `Idle` when an attempt already running succeeds or spends its budget, and writes `retired` into each schedule's `timing_fingerprint`, so the comeback registration is a retime: the next occurrence after it fires, and the retired interval is not caught up. Until then the slot refuses a manual firing. The retire gives the slot no retention deadline; purge it to remove it. Any other landing of an attempt running at the retire, a retry among them, is still cancelled ([known limitations](known-limitations.md)).

### Fixes

- A worker start that read a schedule before another host admitted its last occurrence no longer writes that occurrence back. Before, a deploy racing a finite calendar's final firing restored the admitted occurrence, and a per-occurrence schedule then failed on the root's deduplication key at every pass. Registration now writes a cursor only on a retime or when an orphaned schedule comes back, and a stale copy no longer bumps the schedule's version.
- An admission planned before a deploy changed a schedule's capacity or policies no longer applies. Before, a plan read while a per-occurrence schedule allowed two outstanding roots could admit the second after a deploy lowered `MaxOutstanding` to one, because the change moved no cursor and admission checked only cursor versions. Every schedule a plan read now goes with its declaration version, a slot member the pass left unchanged included, and a manual trigger checks its schedule the same way.
- A namespace suspension now holds an admission already planned. Before, an admission that read a due schedule before the suspension committed still admitted a firing or a fresh root into the suspended namespace, and a manual firing that read the namespace Active did the same. A suspension now takes the namespace's schedule lock, and admission and a manual firing check the namespace after it.
- Run now on a recurring job, `IJobs.RescheduleAsync` on an Idle or Paused slot with no firing outstanding, is rejected while its namespace is suspended. Before, it admitted a manual firing into the suspended namespace, and a worker claimed it; the reschedule now takes the namespace's schedule lock shared, as a schedule trigger does, and a slot whose firing was admitted before the suspension still moves its instant.
- The outbox table refuses a row the relay would mishandle, and the SQLite relay matches an id however a producer spelled it. On SQLite an id is 32 hex digits, with or without its dashes, in either case, and two spellings of one UUID are one row; before, they were two rows that one acknowledgement deleted together, and an id staged without dashes was claimed but never acknowledged. A delay or failure count must fit 32 bits, and on SQLite and PostgreSQL a priority must be 0 to 255, where a larger one stopped every claim batch that held it.
- The outbox table refuses a run instant the relay cannot read. On PostgreSQL it must lie between years 1 and 9999, so `infinity` is refused too; on SQLite it must be UTC text SQLite reads as written, with a space or a `T`, an optional fraction, and an optional `Z`, and the claim reads every such spelling as the same instant. Before, one such row written by a producer's own SQL failed every claim batch that held it, and a SQLite instant ending in `Z` was read in the host's local time.
- On SQLite, a steady flood of enqueues no longer starves the worker. SQLite has one writer, and its busy handler let each fresh enqueue in ahead of a claim that had backed off, so eight callers enqueueing as fast as they could held a worker near zero completions until they stopped. Writes to one SQLite file now queue in the process and run one at a time, in the order they ask. Acta Verify's overload case no longer runs on SQLite: one writer serves the enqueues and the worker alike, so an offer past what SQLite absorbs queues in the caller, not in the database.
- The rate-limit contract states what the meter enforces: at a steady rate, at most `R*(T+W)+B` admissions in any `T` seconds, `W` being the longest a booked turn is honoured late. Before, the guide promised `R*T+B`, which a delayed reservation admitted next to an on-time one could exceed.
- Acta Verify's chaos case reads inconclusive when its outbox producer staged less than its planned cohort, and records how many rows committed and why it stopped. Before, a producer that failed before its first commit left expected and delivered outbox work both zero, and the case could pass. rc.7's chaos evidence staged its whole cohort.
- A metrics listener that throws no longer stops a worker. Before, a listener that threw on an idle claim or wake-wait measurement ended the claim loop while the heartbeat kept the worker Active, so jobs piled up unclaimed. Every measurement now absorbs its listener's exception, and a worker loop that faults for any reason stops the worker's other loops and the host's other workers, so the host sees the fault.
- `explain` reads a job's header, steps, and checkpoints in one statement, so from one snapshot. Before, it read them in three, and a signal landing between them could pair a Suspended job with a wait already Set, so Explain reported no pending wait and offered a cancel for a job that was resuming.
- `IActaTestHost.Schema` reports the schema the runtime uses. Before, a SQLite host reported the name it offered its start callback, while its tables lived in `main`, so SQL written against `host.Schema` found no table.
- An event-recording override reaches a recurring job's slot at once. Before, the slot, one job that lives on, kept the recording it had until the next worker start registered the definition again, and a worker start racing the override could put the old recording back; ordinary jobs still keep the recording they were enqueued with. An override now takes the namespace's schedule lock, and the SQL Server table type `register_slots` loses `event_recording_code`: registration reads the recording from the definition row. A priority override reaches the slot at once too when it is Idle; a slot with a firing outstanding takes it at the next deploy that finds it Idle.
- A schedule waiting on its slot or on its outstanding limit is evaluated as soon as the firing settles. Before, the admitter heard of the settlement only at its next safety poll, so a `CatchUpAll` backlog or a per-occurrence schedule at `MaxOutstanding` admitted about one occurrence per `SafetyPollInterval` (1 s by default) however fast its jobs ran.
- A fleet woken through Redis no longer runs slower than the same fleet polling. Every enqueue published a namespace wake and every finished job a completion wake, and Redis delivered each message to every subscribed process, so sixteen worker processes offered 15,000 jobs a second received hundreds of thousands of messages a second: they completed a fifth fewer jobs than polling, and every write, enqueues included, stalled about a second at a time. rc.7 behaves the same; rc.8's Acta Verify is the first to measure it. A process now publishes a namespace's wake at most once per 10 ms, with one trailing publish for the wakes inside the window, and completion wakes travel on `{prefix}:done:`, which only a process waiting for a job's outcome subscribes to.
- The schedule admitter no longer runs on every enqueue. Each worker's admitter heard every wake of its namespace, so a stream of enqueues in the worker's own process, or arriving over Redis, ran an admission pass of four statements for every one or two jobs enqueued, with nothing to admit. It now wakes for a settled firing or a wake of every namespace, and when idle reads one row a second (the next evaluation and the database clock) instead of four statements.

## 1.0.0-rc.7

Tagged 2026-10-31. rc.7 redesigns scheduling around an admission engine, fixes what an external review of rc.6 found, renames Acta's log fields, and drops dependencies. The schema changes: reprovision, as every pre-1.0 release asks.

### What a consumer must change

**`[JobSchedule]` is now `[Schedule]`.** Only the name changes: `JobScheduleAttribute` is `ScheduleAttribute`, and its arguments, defaults, and diagnostics are the same. Rename the attribute on each scheduled handler.

**`LockScope` is gone.** `JobContext.RunWithLockAsync` takes no scope: a handler lock is scoped to the job's namespace, as a concurrency slot and a rate meter are, so remove the argument. A `LockScope.Global` lock has no replacement; two namespaces that must serialize on one external resource keep those jobs in one namespace ([known limitations](known-limitations.md#execution-model)).

**Schedule overrides are gone.** A schedule's expression and time zone are code-owned: change them in `[Schedule]` and deploy. `ISchedules.UpdateOverridesAsync`, `POST /schedules/{jobNamespace}/{jobName}/{scheduleName}/overrides`, the dashboard's override editor, the `schedule.overrides-updated` event, and the `expression_override`, `expression_effective`, `time_zone_id_override`, and `time_zone_id_effective` columns of `schedules` and `schedules_view` are deleted. Read `expression` and `time_zone_id`. The schedules row's `change_message` is `pause_message`: it holds only the reason for the current pause and is cleared when the schedule leaves Paused; events keep the history.

**An interval schedule is whole milliseconds.** `PT1.0000001S` is `ACTA0122` at compile time and an error at registration, since an occurrence is stored at millisecond precision on every provider and a finer interval would make two ticks one instant. `PT1.5S` is fine.

**A job's kind is stored.** `jobs.job_kind_code` says whether a row is `ordinary` or the `permanent-slot` of a scheduled definition, and `ux_jobs_slot` allows one slot per definition; `jobs_view` carries it as `job_kind` and `job_kind_code`. Registration creates and finds the slot by its kind, and the worker reads the kind from its claim; neither guesses any more from a deduplication key that looks like a job name or from the schedules a row happens to own.

**A schedule's state row says when and why the engine next looks.** `schedules_state.last_advanced_occurrence_at_utc` is gone: no decision read it, and the ledger's `schedule.admitted` and `schedule.skipped` events carry every decision's range. The row gains `next_evaluation_at_utc`, `evaluation_status_code` (`scheduled`, `waiting-for-capacity`, `exhausted`, `evaluation-error`, `slot-unavailable`), and a `version` the admission engine compares and sets. `schedules` gains `interval_anchor_at_utc` (an interval steps from its first registration and never drifts), `misfire_grace_seconds` (60), and `timing_fingerprint`. `ListSchedulesItem`, `GET /schedules`, and `schedules_view` drop the last-advanced instant and carry the next evaluation and the evaluation status. Jobs gain the status `idle`, which a scheduled job's slot holds between firings.

**A handler reset keeps the scheduler's firing envelope.** `checkpoints` gains the kind `firing` (one `sys.firing` slot per scheduled job, Pending while a firing is outstanding and settled with `succeeded`, `failed`, or `cancelled`), which `ctx.ResetStateAsync` leaves in place and `GetCheckpointsAsync` omits: it is the scheduler's record of which schedules admitted the running firing, not the handler's state.

**A schedule is addressed by its path, and the slot job has no key.** `ScheduleLookup` is `(JobNamespace, JobName, ScheduleName)`, resolved through the definition to its permanent slot (`ux_jobs_slot`); the slot's `deduplication_key` is NULL, so `IJobs.GetJobIdAsync(JobLookup.ByDeduplicationKey(ns, jobName))` no longer finds it, and an ordinary root enqueued with the job's name as its key coexists with the slot instead of blocking the worker's start. Find a slot through `GET /schedules` (each item carries the slot's job ref) or the dashboard.

**A scheduled definition says what a failed firing does to its schedules.** `[Job(FiringFailurePolicy = ...)]` is stored as `definitions.firing_failure_policy_code` and read back on `GetDefinition` and `definitions_view`: `continue` (the default) leaves the schedules scheduled, and `pause-scheduling` pauses every active schedule of the definition, with the pause message naming the reason, on the completion or the reclaim that spends the firing's budget; the pause is audited as `schedule.paused` with reason `firing-failed`, and an operator resumes each schedule as usual. A handler's own fail or cancel is not a failed firing: it stops the slot.

**Two more catch-up strategies, and an occurrence can expire.** `MisfireStrategyCode` gains `CatchUpLatest` (30: the latest missed occurrence fires however late, the earlier ones coalesced into it) and `CatchUpAll` (40: every missed occurrence fires in order, one per settlement, within the schedule's capacity); `Skip` and `CatchUpOnce` keep their codes and meaning. `[Schedule(ExpireAfter = "1h", ExpireAction = ScheduleExpireActionCode.Discard)]`, stored as `schedules.expire_after_seconds` and `schedules.expire_action_code` (both or neither, `ck_schedules_expire_pair`), decides occurrences older than the age without work, audited as `schedule.skipped` with the reason `expired`; `Pause` also pauses the schedule with the reason. `EvaluationStatusCode` gains `resumed` (60), which a resume writes so the next evaluation expires the stale backlog once without pausing again. The generator reports an incomplete expiration as `ACTA0126` and an undefined misfire strategy as `ACTA0124`. `ListSchedulesItem`, `GET /schedules`, and `schedules_view` carry the expiration pair.

**A schedule can take its occurrences from a calendar, and any schedule can be limited to open hours.** `[Schedule("business-day", Calendar = "settlement-days")]` binds an occurrence calendar by name, `[Schedule(..., Availability = "office-hours")]` an availability calendar whose `[StartUtc, EndUtc)` windows filter any source: an occurrence outside them is omitted, never shifted. A name resolves afresh at every evaluation and preview, in order: a calendar declared in the process, then the namespace's catalog, then the shared catalog in `sys`. A code calendar is a class marked `[Calendar("settlement-days")]` implementing `IActaCalendar` (the first occurrence after an instant, UTC in and out, null when none remains) or `IActaAvailabilityCalendar` (the window at or after an instant), discovered by the generator into the manifest and created through DI at worker start; `IActaBuilder.AddCalendar(name, implementation)` and `AddAvailabilityCalendar` register one built from data at startup. Code calendars have no versions: a changed one takes effect at the next evaluation, where an occurrence the calendar no longer produces is skipped with the reason `source-changed` and the cursor moves on. `ScheduleExpressionKindCode` gains `calendar` (30; `expression` holds the calendar's name), and `schedules` gains `availability_calendar_name`, carried by `ListSchedulesItem`, `GET /schedules`, and `schedules_view`. A schedule stores the names it binds and nothing about where they resolved. The timing fingerprint covers the names, not where they resolve, so a calendar that moves between code and the catalog keeps the cursor, and the `source-changed` skip heals an occurrence the new source no longer produces. Registration only checks that every name resolves: a name nothing resolves fails the worker start by schedule name, and at evaluation parks the schedule as `evaluation-error` with the reason logged. The generator reports an incomplete source as `ACTA0127` and an incomplete calendar declaration as `ACTA0128`. A preview resolves a code calendar in the host that answers, and on a host without it throws `CalendarUnavailableException`, a 409 problem over HTTP. An `ExpireAfter` that is no duration is reported against `[Schedule]`, not `[Job]`.

**A calendar catalog, per namespace and shared.** `IActaOperations.Calendars` keeps calendar families as data: `calendars` holds one immutable version per row (`calendar_role_code` occurrence or availability, fixed per family; a JSON `definition`; `content_hash`; `calendar_status_code` draft, published, superseded, or archived; `ux_calendars_namespace_name_version`; one published row per family under `ux_calendars_current`), read through `calendars_view`. A family lives in a namespace or in `sys`, the shared scope every namespace binds, and a name belongs to one scope. `SaveDraftAsync` saves the next version against the latest the caller saw (creating a namespace no worker has run in yet), `PreviewAsync` forecasts a version beside the current one with the bound schedules and their overdue flag, `PublishAsync` makes a draft current and retimes every schedule that names the family in its scope (none when the process declares the name in code, which resolves before the catalog) in one transaction under the affected namespaces' schedule locks, its cursor seeded from the new version, refusing while a schedule holds an undecided overdue occurrence unless the caller chooses `OverdueDecisionCode.Discard`, which audits the range as `schedule.skipped` with the reason `retimed`, and `ArchiveAsync` retires a family no live schedule names. Definitions are declarative JSON, validated by path: availability kinds `weekly-availability`, `union`, `intersection`, `subtraction`; occurrence kinds `explicit-instants`, `daily-local-time`, `business-day`, `at-opening`, `union`. Events: `calendar.draft-saved`, `calendar.published`, `calendar.archived`, and `schedule.retimed` per bound schedule. `ListAsync` lists one namespace's families with the shared ones, or every namespace's when `JobNamespace` is null. Over HTTP: `GET /calendars`, `GET /calendars/{jobNamespace}/{calendarName}` (`?version=`), `GET /calendars/{jobNamespace}/{calendarName}/preview?version=`, and the controls `POST .../drafts`, `.../publish`, and `.../archive` (authorizer verbs `calendars.drafts`, `calendars.publish`, `calendars.archive`), whose responses share `ICalendarControlResponse`.

**Scheduling reports itself on the `Acta` meter.** Six instruments join it, each tagged by namespace: `acta.schedule.decisions` counts what each admission pass applied, tagged by decision (`admitted`, `skipped`, `expired`, `blocked`, `exhausted`, `error`); `acta.schedule.lag` records how far past its nominal instant an occurrence stood when admitted; `acta.schedule.due.age` records how long past its evaluation instant each due schedule stood when a pass read it, so its maximum is the overdue frontier; `acta.schedule.pass` records a pass's wall time and `acta.schedule.stale` counts the plan groups another host moved first; `acta.firing.start.delay`, tagged by job name too, records the time from a firing's admission to the attempt that first ran it, by the worker's clock.

**A reschedule runs a recurring job now.** `IJobs.RescheduleAsync` takes a nullable instant, null meaning now, and `POST /jobs/{jobRef}/reschedule` accepts an empty body; the dashboard's job page gains a Run now control beside Change run time. On an `Idle` permanent slot, or a Paused one with no firing outstanding, the reschedule is a manual firing at the instant (a `sys.firing` envelope of kind `manual`, a fresh failure budget), and the slot returns to `Idle` when it settles; a slot mid-firing keeps its firing and moves its instant. As at rc.6, a reschedule to now runs the job.

**A scheduled definition can deliver each occurrence as a fresh root.** `[Job(ScheduledDelivery = ScheduledDeliveryCode.PerOccurrence)]`, stored as `definitions.scheduled_delivery_code` and immutable once registered, replaces the permanent slot with one ordinary root job per admitted occurrence: `jobs.schedule_id` names the admitting schedule (`jobs_view` carries it, and the operator guide's capacity-drift recipe reads it), the root's input is the definition's default input, which registration now stores as `definitions.default_input_format_id` and `definitions.default_input` so any host admits it, and its deduplication key is `sys.occurrence.{schedule_id}.{ticks}`. `[Schedule(MaxOutstanding = 1, FullBehavior = ScheduleFullBehaviorCode.Wait)]` (`schedules.max_outstanding`, `schedules.full_behavior_code`) bounds a schedule's unsettled roots, counted in `schedules_state.outstanding_count`: every terminalization releases one, a restart of a finished root re-charges or is Rejected, a manual trigger admits a charged root, and a `Permanent` definition's schedules allow exactly 1 (`ACTA0124`, `ACTA0125`). A per-occurrence schedule's skip and ended pause are audited against the definition (`entity_code = definition`). `schedules.job_id` is NULL for such a schedule; `GetDueSchedules`, `ListSchedules`, `schedules_view`, `GET /schedules`, and the dashboard carry the delivery and capacity fields; the claim projection carries `schedule_id`; and `complete_executions` gains `p_has_schedule` on PostgreSQL.

**Scheduling is admission-driven, and a scheduled job's slot is `idle` between firings.** The admission engine, one loop per worker namespace, evaluates each schedule when it is due, admits one firing per slot per pass with every due schedule coalesced into it, moves the cursor at admission, and writes the firing's envelope to `sys.firing`; the claim then runs the slot like any job, and completion settles the envelope and wakes the schedules that waited for it. The slot carries no cursor of its own: it is `idle` with no `next_run_at_utc` until a firing is admitted, `ready` while one is, and `idle` again when it settles. A firing retries under `MaxAttempts` like a one-shot, with the count zeroed at each admission; a spent budget returns the slot to `idle` with the envelope `failed` and the attempt's `job.execution-failed` event, never `job.failed`, and a reclaim does the same for a lost attempt. `JobContext.TriggeringSchedules` (name, occurrence, time zone, covered-through) and `JobContext.FiringId` replace `TriggeringScheduleNames`. `job.recurring-rolled-over` is gone; the decisions are `schedule.admitted`, `schedule.skipped`, and `schedule.retimed`. Registration never moves a slot: a new slot is `idle`, a redeploy with an unchanged schedule changes nothing, and a changed expression, time zone, or interval anchor retimes the schedule, discarding the old timing's undecided occurrences. Pausing a schedule no longer pauses or re-arms the slot; resuming one puts it in front of the admitter at once with its cursor kept, and the misfire policy applies at the next pass. `TriggerNowAsync` admits a manual firing on an `idle` slot and is rejected otherwise. A job pause, cancel, restart, and resume accept an `idle` slot; a restart is rejected while a firing is outstanding, and a restart or resume with none returns the slot to `idle`. A permanent slot is purged only by deliberate decommission: `idle`, `failed`, or `cancelled`, no firing outstanding, and no live schedule of a live definition pinning it. A retire cancels an `idle` slot with retention and settles its envelope.

**A schedule has its own identity.** `schedules` is keyed by a new `schedule_id`, unique on `(definition_id, schedule_name)`, and `schedules_state` is keyed by it alone, so a cursor row no longer carries the slot job and the name. `schedules_view` leads with `schedule_id`. Registration keeps a schedule's identity across deploys; a renamed schedule is a new one. The HTTP and .NET surfaces are unchanged (a schedule is still addressed by `namespace/job/schedule`), but a `GET /schedules` continuation cursor from an earlier build is invalid: start the page again.

**A typed wait or result read refuses a job whose definition returns another type.** `JobHandle<T>.WaitAsync`, `WaitAsync<T>`, and `RunAndWaitAsync<T>` throw `InvalidOperationException` on their first read of a job whose registered definition produces a result other than `T`, or none, whatever its outcome. `JobHandle<T>.GetResultAsync`, `GetResultAsync<T>`, and a handler's typed child result read throw instead of decoding such a job's stored result, in the same round trip. Before, a deduplication key shared across definitions handed back the other definition's job, and its wait decoded the foreign result leniently: success, with defaults in the missing members. A job this process does not register decodes as before.

**`JobOutcome.TerminalStatus` is `Status`, and a failed wait names the job by its ref.** An outcome's status is the job's last observed one, which is `Ready` or `Running` when `IsTimedOut` is set, so the member no longer claims it is terminal; `IsSuccess`, `IsFailed`, `TryGetValue`, and `ValueOrThrow` behave as before, and there is no alias. `JobFailedException` gains `JobRef`, its constructor is `(long jobId, JobRef jobRef, JobStatusCode terminalStatus)`, and its message, the wait-timeout `TimeoutException`, and `ValueOrThrow` identify the job by that ref, the one the dashboard and the HTTP API address, instead of the numeric id. Rename the member at every read.

**Every log field Acta writes is renamed, and saved log queries must follow.** Each field carries the `Acta` prefix so none can clash with an application's own: the job scope on every handler line is `ActaJobId`, `ActaJobName`, `ActaNamespace`, `ActaExecutionNumber`, `ActaWorkerId`, and `ActaCorrelationKey`. Numbers are `long`. `Operation`, `Outcome`, `Reason`, `Count`, and `SubjectRef` are gone, because each meant something different on different lines; their values now read in the message or in `ActaDetail`. The `ACTA ALERT` line carries `ActaAlertRef`, `ActaJobRef`, and `ActaAlertKind`. Acta no longer logs a line per completed job, nor any Debug line. The operator guide's "Logs" section shows how to quiet a failure storm.

**Native AOT with a multi-parameter handler:** declare the input record yourself. The developer guide used to say to add the generated `Args` record to your JSON context, which cannot work. System.Text.Json's generator never sees a generator-emitted type.

## 1.0.0-rc.6

Tagged 2026-10-26. Upgrading from rc.5 takes the changes below.

### What a consumer must change

**Drop and reprovision every database an rc.5 build provisioned**: the baseline is re-cut, and nothing translates it.

**The whole model now speaks one semantic vocabulary.** Tables: `runtimes` is `jobs_state`, and `schedules_state` is new (the schedule cursor split below). Columns carry qualified names: `<entity>_id` identities, domain-qualified codes (`job_status_code`, `schedule_status_code`, `worker_status_code`, ...), `event_recording_code` replaces `audit_level_code`, `max_concurrent_executors` replaces `max_concurrency`, `host_name` replaces `host`, tags attach by `entity_code`/`entity_id` with `tag_name`/`tag_value`/`tag_value_search`, and steps store `failure_code`/`failure_message` with their own `StepFailureCode` family. Every index, check, routine, table type, and view follows; SQL that reads base tables or views needs the new names.

- View changes operators will hit first: `jobs_view` raw code columns are `job_status_code`/`job_priority_code` (decoded `status`/`priority` stay); `schedules_view` exposes `schedule_name`, `next_occurrence_at_utc`, `last_advanced_occurrence_at_utc`, and `change_message`; `workers_view` has `max_concurrent_executors` and `host_name`; `tags_view` has `entity_kind`/`entity_code`/`entity_id`; `definitions_view` drops the effective-as-bare convention — the bare policy column is the declared default, with explicit `_override` and `_effective` variants; `definitions_view.definition_name` replaces `job_name`.
- `events` is a compact generic ledger: fifteen typed columns on the `(entity_code, entity_id)` subject pair. One outcome event per attempt replaces `job.execution-finished` plus its status triple: `job.execution-succeeded`, `job.execution-failed`, `job.execution-orphaned`, `job.execution-yielded`, and terminal `job.failed`. The actor, from/to status, execution status, and reason columns are gone — causes live in the event code and the JSON `details` payload (`details_format_id`/`details` pair, same convention as input/result/value); human text is `event_message`. Events no longer store `job_ref`: joins supply refs while the row lives, and an explicit purge leaves one `job.purged` tombstone whose details snapshot the ref and correlation key once.
- `events_view` has the new shape (`entity_kind`, `entity_id`, `event`, `execution_number`, `duration_ms`, `event_message`, `details_text`); `GET /events` items expose `eventId`, `entityKind`, and `entityId` (the one deliberate numeric identity on the wire — the subject survives row deletion), and the `actorCode`/`reasonCode` filters are gone.
- Schedules split: `schedules` keeps the declaration and operator lifecycle (status, pause, `change_message`, `version`); `schedules_state` holds only the cursor. A fire advances the cursor without bumping the config `version`, so an operator's `expectedVersion` is no longer invalidated by a running schedule. Orphaned and retired schedules carry a NULL cursor; `GET /schedules` with `liveOnly=false` lists them, the default live list does not.
- Wire renames: `maxConcurrency` → `maxConcurrentExecutors`, `host` → `hostName` (workers); `nextRunAtUtc` → `nextOccurrenceAtUtc` and `lastRunAtUtc` → `lastAdvancedOccurrenceAtUtc` on schedule items and control responses; `nextRunsUtc` → `nextOccurrencesUtc` (preview); `auditLevel*` → `eventRecording*` (definitions and overrides); the CLI explanation's `steps[].state` is `steps[].status`. Job-level `nextRunAtUtc` keeps its name: a run is a scheduled instant.
- .NET: `[Job(EventRecording = ...)]` replaces `AuditLevel`; `TagScopeCode` is replaced by the shared `EntityCode` (all entities, numbered alphabetically by tens); `EventReasonCode`, `ActorCode`, and `ExecutionStatusCode` are gone; schedule records speak occurrence vocabulary.
- SQL Server table types drop `_batch` (`enqueue_jobs`, `enqueue_tags`, `complete_executions`, `register_definitions`, `register_slots`, `register_schedules`) and their columns take full names; the `enqueue_job`/`enqueue_jobs` routine tag parameters are `@p_tags` / `p_tag_name`/`p_tag_value`/`p_tag_value_search`, with `p_job_priority_code_override`, `p_parent_job_id`, and `p_lane_name`.
- `PurgeAsync` can now answer a blocked condition (`JobPurgeBlockedException`, HTTP 409): a job whose alert-required events the alerts projector has not consumed cannot be purged until it runs; automatic retention defers those jobs the same way.

- `JobDescriptor` loses `InvocationKind`, `RequiresJobContextParameter`, and `RequiresCancellationToken`, and `JobInvocationKind` is gone: the generated invoker already carries those facts. Only code that builds descriptors by hand changes.
- `JobStatusCode.IsClaimable` is gone: compare the status with `JobStatusCode.Ready`.
- `JobStatusCode.IsActiveExecution` is gone: compare the status with `JobStatusCode.Executing`.
- `StepStatusCode.IsTerminal` is gone: a step is terminal when it is `Succeeded`, `Exhausted`, or `Interrupted`.
- `JobOutcome.IsCancelled` is gone: check `TerminalStatus == JobStatusCode.Cancelled` on an outcome that is not `IsTimedOut`.
- `ParallelOutcome.GroupName` and `MapOutcome<TKey>.GroupName` are gone, with their constructor parameters: the handler already holds the name it passed.
- The `ParallelOutcome` indexer is gone: read a branch as `outcome.Branches["branch-name"]`.
- `IAlertTransportRegistry` is internal: register an `IAlertTransport` and the alert job resolves it by its `TransportKind`.
- `ITags.ReplaceAsync`, `UpsertAsync`, and `RemoveAsync` lose their `reasonMessage` and `actor` parameters, which no tag write ever recorded.
- `INamespaces.ListNamesAsync`, `ListNamespaceNamesQuery`, and `ListNamespaceNamesResponse` are gone: call `ListAsync` and read each item's `JobNamespace`.
- `POST /jobs/{jobRef}/purge` takes an empty body: a `reasonMessage` member now answers 400, since purge never recorded it.
- `GET /jobs/{jobRef}/detail` drops the top-level `tenantName`: read `job.tenantName`.
- `CodeManifests.MarkdownReport` is gone: the code families are documented in `docs/reference/code-families.md`, and `CodeManifests.All` stays.
- A job's input and output type names must be printable ASCII and at most 512 characters: registration refuses others, and the generator reports ACTA0103 at compile time.
- `TagMutationAction` is gone: tag writes answer `ControlAction` (`Applied` or `NotFound`), with the same wire values.
- `JobAttribute.Tags` is gone; it never had an effect.
- `ActaEndpointOptions.ControlConfirmationHeaderValue` is gone: the confirmation header's value is always `true`, and only its name is configurable.
- `ExecutionStatusCode.ChargesFailureBudget` is gone: a `Failed` attempt charges the budget only when it retries, which the status alone cannot say.
- `JobPayload.FromBytes` and `CopyBytes` throw `ArgumentException` for json bytes that are not valid UTF-8 or hold a NUL byte; binary and custom formats are unaffected.
- `JobAttribute.RecurringResultCap` and `JobDescriptor.RecurringResultCap` are gone: a job stores one result, and a handler that wants more history keeps it itself.
- `ActaJobs.SysOutbox()` returns `JobCall<NoInput>`: the outbox relay returns no result and keeps its last tick's counts in the slot's `outbox-status` variable.
- `jobs_view` replaces `last_result_execution_number`, `last_result_format`, `last_result_text`, and `last_result_created_at_utc` with `result_format` (`none` when there is no result) and `result_text`.
- `tags_view` has no namespace columns: join `jobs_view` for a job tag's namespace.
- The job explanation's `view-result` action is gone.
- `events_view.worker_id` is 0, not NULL, for an event no worker wrote; `worker_ref` stays NULL for it.
- A ref prints as its prefix and the Guid's 32 lowercase hex digits, such as `job_01a14f4e954e7bf68ac609f3fcad8e3d`, and parses only in that form, with the hex in any casing. The Crockford form, a dashed or bare Guid, and an uppercase prefix no longer parse, and the HTTP routes answer 400 for them. `job.purged` names the job the same way.

**Typed enqueue answers a handle, and payloads are JSON or bytes.**

- A typed enqueue or a call answers `JobHandle`, a record deriving from `EnqueueJobResponse` that adds `GetStatusAsync`, `WaitAsync`, `GetResultAsync`, `CancelAsync`, and `ExplainAsync`; a result job's call answers `JobHandle<TResult>`, and its result type is checked before the enqueue. A `ValueTask<EnqueueJobResponse>` variable or wrapper becomes `ValueTask<JobHandle>`. A test double of `IJobs` returns `new JobHandle(jobs, jobId, jobRef, action)`.
- `IJobs.WaitAsync(job, timeout)` and `WaitAsync<TResult>` wait on any job; `IJobs.GetHandleAsync(jobRef)` rebuilds a handle; `JobOutcome` carries `JobRef`. `RunAndWaitAsync` throws when its job is purged while it waits, instead of timing out as `Ready`.
- `ScheduleAsync(input, TimeSpan)` and `ScheduleAsync(input, DateTimeOffset)` enqueue one job for later, with call and transactional forms.
- A manifest's job members are factories instead of `JobContract` properties: `ShippingJobs.ShipOrder(order)` returns the job's `JobCall`, which `EnqueueAsync` and `ScheduleAsync` take with a `configure` callback for options and `RunAndWaitAsync` with its `JobExecutionOptions`, so `jobs.EnqueueAsync(ShippingJobs.ShipOrder, order)` becomes `jobs.EnqueueAsync(ShippingJobs.ShipOrder(order))` and a no-input `ShippingJobs.Sweep` becomes `ShippingJobs.Sweep()`. The contract overloads of `EnqueueAsync`, `RunAndWaitAsync`, and `ScheduleAsync` are gone, with the conversion from `JobContract<TInput, TResult>` to `JobContract<TInput>`.
- A handler may take several input parameters before `JobContext` and `CancellationToken`, which used to be ACTA0103: they travel as one generated record, `ShippingJobs.{Job}Args`, stored as JSON keyed by the parameter names. Such a handler cannot carry `[JobSchedule]` (ACTA0123), an interface parameter other than a collection is ACTA0103, and a Native AOT app registers the record in its `UseJsonPayloads` context.
- The text payload format is gone: a typed value with no explicit format is JSON unless it is `byte[]` or `ReadOnlyMemory<byte>`, scalars included, so a scalar handler's stored input reads `"order-42"` or `42`. `JobPayload.Text`, `JobRequestBuilder.Text`, `JobPayloadFormat.Text`, and `TextJobPayloadSerializer` are gone; `JobPayload.Json(string)` and `JobRequestBuilder.Json(string)` replace them without reflection. `[Job(Format = "text")]` no longer compiles (ACTA0132).
- Under reflection-free Native AOT, Acta supplies JSON metadata for the standard scalars; an enum input or result goes in the app's `UseJsonPayloads` context like any other type. JSON has no NaN or Infinity, so serializing one throws at enqueue.
- A json payload is exactly one strict JSON value: `JobPayload.FromBytes` and `CopyBytes` reject comments, trailing commas, a second value, and an empty body, the JSON serializer reads strict JSON, an HTTP or CLI signal like that answers 400 or a usage error, and an outbox row like that quarantines.
- HTTP: `POST /jobs` and `POST /jobs/{jobRef}/input` drop the `text` field; a payload's `json` field is the stored JSON text as a string, never a nested object, and a stored row within the inline size cap that is not strict JSON reads as `base64` with `malformed: true`.
- The operator views decode only json payloads into the `*_text` columns.
### Behaviour changes

- Automatic alerts are independent of the recording level: an enabled alert profile captures the failed, orphaned, terminal, and recovery transitions durably even at `EventRecording = Off`, retention never sweeps an alert-required event the projector has not consumed, and a poison event stays recoverable until replayed or dispositioned. One documented gap: a recurring job restarted after a terminal failure does not auto-resolve its incident at `Failures`/`Off` (see known-limitations).
- `Failures` recording now records every failed attempt, the orphaned attempt a reclaim writes, and the success that recovers from a failure — not only terminal failures.
- `failure_count` saturates at 32,767 instead of growing without bound; it still resets on success, and `MaxAttempts` registration caps at the same ceiling. Alert escalation's `occurrence_count` is unaffected.
- A schedule fire no longer bumps the schedule's `version` or `modified_at_utc`; only operator edits do.
- A retired definition's schedules are inert everywhere. Registration, a completion planned before the retire, and the schedule verbs (pause, resume, overrides, trigger) can no longer revive their cursors or wake the slot. Each schedule verb answers `NotFound`. Resuming or restarting a retired slot is no longer rejected: the worker claims it and lands it `Cancelled` without running the handler.
- Each namespace has one schedule lock. `RetireDefinition` and a worker's schedule registration take it exclusive; a completion that fires a recurring slot and the schedule verbs take it shared. A retire or registration therefore waits for the namespace's in-flight fires and verbs to commit, and they wait for it; fires never wait for each other.
- A worker start skips its schedule registration, and that lock, when the namespace holds the start's catalog hash and no stored cursor or slot would move. `namespaces.catalog_hash` now hashes the whole registered catalog and is written by that registration, not by the worker start.
- On SQL Server, `correlation_key` and the tag search column compare bytewise, as they already did on PostgreSQL and SQLite. A correlation filter no longer matches a key that differs only by case, and a tag filter no longer matches full-width letters, a different emoji, or a sharp-s spelling.
- A correlation filter is trimmed and checked like a key, and a tag value filter ignores surrounding whitespace, on every provider.
- A job ref resolves only while its job row exists. Once retention purges the job, by-ref reads return null and the by-ref HTTP routes answer 404; its events stay queryable in `events_view`, and by job id.
- Retiring a definition also stops the jobs running when it lands: the attempt finishes, then the job lands Cancelled with `JobDefinitionRetired` instead of retrying, rescheduling, or rolling a recurring slot over. Workers learn of a retire on their next heartbeat.
- Worker events carry a null actor and name their worker by `worker_id`. Retention keeps a worker row as long as events can name it: the longer of `WorkerRetention` and `JobEventsRetention`, counted from the newest event about the worker, recovery's included, and never while it still leases an Executing job.
- Automatic retention also deletes expired tenant events, which live in the `sys` namespace.
- An instance handler registered in DI is the instance invoked, so a typed `HttpClient` keeps its configuration; a Singleton registration is shared by every concurrent attempt. An unregistered handler is constructed per attempt and disposed when the attempt ends (`DisposeAsync` first), and a dispose that throws fails the attempt.
- A stale `expectedVersion` on definition overrides, retire, or schedule overrides answers `VersionConflict` (409 `versionConflict`) instead of `Rejected`, as every other versioned verb already did. `SetDefinitionOverridesResponse` and `RetireDefinitionResponse` carry the definition's `Version`.
- The alert, definition, outbox, and tag response interfaces extend `IControlResponse`; the versionless families report a null `Version` and keep their JSON shape.
- A failed attempt that retries within budget records execution status `failed` (200), not `rescheduled` (150), which now means only a handler-requested reschedule. A query that counted retries by 150 counts 200 with to-status `ready`.
- A signal body that is not UTF-8 or holds a NUL byte answers 400; an outbox row like that quarantines.
- The descriptions of `job.rescheduled`, the `Failures` audit level, the `OnFailure` alert profile, the `job` and `worker` actors, and the `failed` execution status now say what Acta records; behaviour is unchanged.
- A job stores at most one result, on its `jobs_state` row: a one-shot job's terminal success, or a recurring job's latest successful occurrence. Every claim and every restart clears it, so a running attempt or a failed occurrence leaves the job without one. The `results` table and its per-execution history are gone, and a successful completion writes one row instead of two.
- The dashboard's job view shows the input and the result beside the status; the Input and Result tabs are gone.
- On SQL Server, events are clustered by worker, then id, so each worker appends to its own end of the table instead of every worker contending for one last page; PostgreSQL keys events the same way. A purge deletes events by that pair.
- A generic input or output type is stored without assembly versions (``System.Collections.Generic.List`1[MyApp.Line]``), so an application version bump no longer reports contract drift for it.
- Startup and migration apply refuse a database whose migration history names a baseline this build does not ship, and the error names it. Applied over an earlier release candidate's database, the re-cut baseline changed nothing and left that cut's schema in place.
- Three metrics join the `Acta` meter: `acta.executions.fenced` counts attempts stopped because a write found their job held by another execution, `acta.lease.headroom` records how long an attempt had left on its lease when a renewal confirmed it, and `acta.alerts.lag` records how far the alert projector's cursor stood behind the database clock when a pass began.
- The SQLite floor is 3.51.0, up from the documented 3.42: batch completion uses `jsonb_each`, which SQLite added in 3.51.0, so an older engine started but could not complete a job. Startup now reads `sqlite_version()` and refuses an older engine with an error naming both versions; the engine `Microsoft.Data.Sqlite` bundles clears the floor.

### Fixes

- A handler write from an attempt that no longer holds its job changes nothing. Checkpoints of every kind, waits, timers, steps, notes, a state reset, and a child start each check the job is still executing that attempt on that worker, under a lock on its `jobs_state` row held to commit. Before, an attempt cancelled, restarted, or reclaimed under a running handler could overwrite the next execution's variables or mark its at-most-once step Interrupted until the next heartbeat stopped it. A refused attempt now stops as a lost lease does, with no completion and no retry charged, and a note from it is no longer recorded.
- On SQLite, a step whose retry instant came due while `start_step` ran is answered Suspend. Each of the script's statements read the clock afresh, so the attempt was invoked without being counted, and a budget of two attempts could run the body three times. On every provider a step's next attempt now clears the retry instant it spends.
- A bounded group wait that runs out of time resumes its parent in one pass, however many members it holds. Each member's latch is armed with the group's stored deadline itself, and a latch first armed past it times out at once. Before, each member first reached after the deadline armed a fresh one-second bound and suspended the parent again, so a group's overshoot grew with its size.
- Typed `RunAndWaitAsync` reads the result of the execution it saw succeed. After a restart whose second result was too large to store, it returned the first execution's result; now it throws.
- Typed `ExecuteChildAsync` reads the result of the child execution that released the parent, and throws when that execution stored none. It returned an older execution's result after a restart, and a value-type default such as 0 for a child that stored no result.
- On SQLite, the recovery pass's lane repair seeks the lanes primary key instead of scanning and sorting every lane inside the write transaction.
- The checkpoint and tag shape checks accept code values this build does not name, so a future checkpoint kind or status, or tag scope, needs no table change.
- A malformed name or key in a query string or route segment answers 400 instead of a sanitized 500. `GET /tenants/{tenantName}` answers 400 for a name that is not a tenant name, where it answered 404.
- A payload type whose state is get-only properties set through a constructor travels as JSON. It was classified as carrying no payload, so the handler received default values and a result of that shape was dropped.
- Two job names that differ only in `.` and `-`, such as `send.mail` and `send-mail`, compile and warn ACTA0106, as do names matching a member the manifest class declares or a type it uses; they failed the build with duplicate members.
- The dashboard's schedule editor saves with the version its draft was opened at, so another operator's change made while the editor was open is refused instead of silently reverted.
- An outbox row whose tags hold a null entry, or that fails reconstruction any other way, is quarantined alone; it stalled its whole claimed batch on every relay tick.
- A stale relay pass no longer deletes an outbox requeue or discard it never applied. A command parked after another pass consumed the previous one starts at the same version, and the stale pass's consume matched it by version; a pass now consumes only the command it read.
- An outbox requeue or discard replayed after a relay crash between its source change and its evidence records one event naming the rows it changed, and changes no other row. The relay now stores the rows a command targets in the command before it changes them, and records the evidence and consumes the command in one statement; a replay named no rows, a crash after the evidence recorded the command twice, and a stale pass of a command that targets every quarantined row swept rows quarantined since.
- On SQL Server, the outbox relay's finalizes and the operator requeue and discard seek the producer's table by key, so a producer transaction still open on the table no longer holds them up. On a small table they scanned it and waited for that transaction to end, and a long one failed the relay tick.
- A job of a retired definition that recovery returns to Ready is claimed and landed Cancelled, even by a worker that had stopped claiming the definition for want of its handler; it stayed Ready forever.
- On SQLite, a job due before 1970 is claimed; the claim never reached it, and the worker retried every poll floor.
- A Redis wake whose jitter draw was zero no longer disables remote wakes for its channel until the process restarts.
- A metric listener that throws no longer stops a worker's recovery passes for good.
- Application types in the root namespace named like the types generated code uses, such as `JobContext` or `ValueTask`, no longer break the build: the generated manifest names every type with `global::`.
- On SQL Server, rate-limited jobs no longer deadlock in `reserve_rate`. A call on a meter whose bucket was not yet stored took a range lock over the gap that holds the meter's reservations and the next meters, and a chaos run with three meters recorded 150 to 190 deadlocks, each retried after the deadlock monitor picked a victim. Calls on one meter now serialize on the meter's own lock.
- On SQL Server, a completion batch no longer deadlocks with a wait or a raise on the same job's slots. The batch probed an awaited slot under `HOLDLOCK`, locking the gap after it, and only later asked for a parent latch's lock that a waiting raise held. It now takes every slot lock in one name-ordered pass before it touches a slot row.
- A note written with `ctx.NoteAsync` records the worker whose attempt wrote it. It stored worker 0, so on SQL Server every worker's notes appended at one point of the events key.
- On SQL Server, a binary parameter bound without a size is declared `varbinary(max)`, so a statement keeps one cached plan instead of one per payload length.
- Under reflection-off Native AOT, `sys.alerts` writes and reads its poison-event records when the application's JSON resolver has no `string` metadata: Acta's own context now covers every value Acta persists, `string` and `long` included. The write failed, and since it lands before the cursor moves, the projector could not get past that event.
- A `[Job]` handler named with a C# keyword, declared as `@event` or named `await`, compiles: the generated invoker writes the name with its `@`, as it now does a keyword segment of the root namespace. It emitted `Handlers.event()` and failed the build.
- A graceful drain waits for the descendant cancel that a completion repeating apart starts when it lands. It read which cancels to wait for before those completions landed, so the stop that followed could cut a handler-cancelled job's walk short and leave its descendants running.
- A cancel walks the job's descendants to the end when its caller stops waiting. The dashboard's cancel walked on the request's token, so a closed tab or a proxy timeout on a large tree left children running.
- When a handler cancels its job, a descendant walk that fails partway runs again from the root until it finishes or the worker stops. A database error ended the walk and left the rest running.
- A recurring job whose default input encodes to zero bytes, such as a handler that takes `ReadOnlyMemory<byte>`, registers at worker start. Its slot was written with NULL bytes beside a payload format, which the input pair check refuses, so the start failed; on SQLite a batch enqueue of an empty text or byte payload failed the same way.

### Evidence

The engine was certified on `599e28e8` with the Acta Bench full profile on SQLite, PostgreSQL, and SQL Server, in seven bundles reported in [`docs/benchmark.md`](./reference/benchmark.md). The bench changes between the bundles touch only `tools/Acta.Bench` and its tests; `src/` is the same in all seven.
- **Result.** No case failed safety or liveness in any bundle, and every trial's ledger passed the certification checks.
- **Chaos certification.** F09 passed at 1,000,000 jobs on PostgreSQL and on SQL Server: 24 workers of 64 executors, a worker killed every 5 s for 7 minutes, 84 and 83 kills, every one of a busy worker whose work was reclaimed, and 16 ledger checks with no violation. SQLite passed at 10,000 jobs on 3 workers.
- **Bench defects found during the run**, each fixed in the bench alone:
  - The memory guard counted the database container's page cache as used memory and stopped PostgreSQL in the 64 KB payload trials. It now counts only memory the kernel cannot reclaim (`fb8f8414`).
  - The owned PostgreSQL server allowed 500 connections, too few for the full chaos fleet. The refused attempts exhausted the host's TCP ports, so a replacement worker could not start. It now allows 2,500 (`fb8f8414`, `988764e6`).
  - A replacement worker whose SQL Server login timed out on the saturated host ended F09. The bench now starts a replacement again, up to three times, as a process supervisor would, and records every failed start; neither rerun needed one (`988764e6`).
  - 10,000 chaos jobs drained before enough kills hit busy workers on the servers. The reruns seeded 1,000,000, the scale useacta.net states.
  - The full profile validated only at 0.8 of a case's discovered rate, which discovery's 15 s trials can overstate, so a case that missed it had no validated rate at all. A case where no rate holds at 0.8 is now measured at 0.7, 0.6, and 0.5 in turn (`05e5c27c`).
  - On Linux, a bench worker read its controller's start time a few milliseconds off and stopped before it was ready; the tag's NativeAOT check found it. The evidence ran on Windows, where the two reads agree, and the release carries the fix (`5511252d`).
- **Reruns.** PostgreSQL `--full` on `fb8f8414`, then F09 alone on SQL Server and on PostgreSQL on `988764e6`, both passing. Then every capacity row still unvalidated, on `05e5c27c`: P01 on SQLite; M02, M04, O02, O03, and P01 on SQL Server; L01, C01, P01, I05, M03, M04, O03, E01, and E03 on PostgreSQL. The other SQLite and SQL Server cases come from `599e28e8`.
- **Capacity.** A row is validated only when an arrival rate passes every independent validation trial. One PostgreSQL worker of 64 executors validated at 7,680 no-op jobs per second end to end; at 8,960, one of five trials was limited by the bench's own load generator, and at 10,240 the backlog grew. Still INCONCLUSIVE, with correctness passed: O03, one hot concurrency key, on PostgreSQL and SQL Server; I05 on PostgreSQL, which sustained about 310 roots/s, below its lowest frozen rate of 400; and PostgreSQL's E01 soak, where the load generator fell behind. SQL Server's E03 offered 3,200 roots/s without growing the backlog, so it established no overload.
- **useacta.net.** The homepage states 7,680 fully executed, durably completed jobs per second from L01 and a 77,662 roots/s steady drain at 8 workers from L04. The batch-enqueue and pickup-latency figures from rc.5's round are gone, since this bench has no comparable row. The million-job line points at this evidence.

## 1.0.0-rc.5

Tagged 2026-10-17. Upgrading from rc.4 takes the changes below.

### What a consumer must change

**Drop and reprovision every database**, including one an earlier rc.5 build provisioned: the migrations table changed shape and nothing translates it.

Packages and namespaces:

- `Acta.Relational` and `Acta.Runtime` are gone; their code ships in `Acta`, which every provider brings. Drop the references; `using Acta.Runtime;` becomes `using Acta;`, a log filter on `Acta.Runtime.X` becomes `Acta.X`, and the system-job manifest `RuntimeJobs` is `ActaJobs`.
- Each package has one namespace, its own name: replace sub-namespace usings (`Acta.Postgres.Configuration`, `Acta.AspNetCore.Configuration`, `Acta.Testing.Hosting`, ...) with the package root.

Configuration:

- `UsePostgres`, `UseSqlServer`, and `UseSqlite` take `Action<SqlProviderOptions>`; the per-provider options types are gone. On SQLite the schema is always `main`.
- An outbox source is chosen by connection string: `source.UsePostgres(connectionString)` and its siblings; the `XOutboxSourceOptions` types are gone.
- `JobsOptions.ExecutionProfile`, the `ExecutionProfile` enum, and `JobsOptions.ClaimBatchSize` are gone. A worker claims for every free executor; lower `MaxConcurrentExecutors` to claim less.
- `DriverVersionPolicy` is gone: a driver of another major version logs one warning and runs.

Jobs and statuses:

- `JobStatusCode.Dispatched` (40) is gone; a claim moves a job straight to `Executing`.
- `sys.recovery` is gone: crash recovery runs on the workers' heartbeat. `RegisterSystemJobs` still turns it off.
- A claim writes no `job.execution-started` event: `EventCode.JobExecutionStarted` (40), `ExecutionStatusCode.Executing` (50), and `ExecutionBehavior.Live` are gone. An attempt is recorded once, by `job.execution-finished`.
- `EnqueueBatchAsync` takes at most 1,000 rows (was 5,000).
- Tags attach only to tenants, namespaces, definitions, and jobs: `TagTarget.ForSchedule`, `ForWorker`, `ForAlert`, `ForEvent`, their `/tags` routes, and the `Tags` filter on the schedule, worker, alert, and event lists are gone.
- Durable settings (`ISettings`, the `settings` table, event 160) are gone.
- The `Acta.Testing` scenario API (`Scenario.For`, `ScenarioSession`) is gone: drive jobs through `IActaTestHost`.
- The gauge `acta.executing` is `acta.jobs.inflight`, filtered to `state = executing`.
- An uncaught `StepExhaustedException` fails the job at once with `job.non-retryable-exception` instead of spending its retry budget, since every retry would replay the exhausted step; on a recurring job it rolls over to the next occurrence.
- `NotSupportedException` and `NotImplementedException` roll a recurring job over to its next occurrence, alerting like any failure, instead of ending its schedule.
- `ctx.FailAsync`, `CancelAsync`, `RescheduleAsync`, and the waits called inside a step body decide the job, as they do from the handler body, instead of failing the step.
- An interval schedule fires at most once a second: a shorter interval is `ACTA0122` at compile time, and the override verb refuses one.

Identifiers:

- A name (namespace, job, schedule, signal, tag, lane, tenant, rate meter) is ASCII `dotted.kebab-case`, lowercased on input. A key (deduplication, concurrency, correlation, lock) is printable ASCII kept exactly as given, so `Order-1` and `order-1` are two keys. Display text is any Unicode.
- Two inputs tighten: a correlation key must be printable ASCII, and a tenant or lane must be a valid name.
- `IdentifierSyntax` and `AdminTextLimits` are replaced by `NameSyntax`, `KeySyntax`, and `TextLimits`.
- Renamed to match: `TenantKey` is `TenantName` (and `tenant_key` is `tenant_name`, in the outbox table too); `[Job(RateName = ...)]`; `alerts.deduplication_key`; `events.actor` and the `actor` argument of control verbs. On SQL Server an outbox table's `deduplication_key` and `concurrency_key` take the collation `Latin1_General_100_BIN2_UTF8`.

Responses and read models:

- Every list returns its own `ListXResponse` of `ListXItem`, every get its own `GetXResponse`, and every control verb its own `<Verb><Noun>Response`, replacing `PagedResult<T>`, the `*Detail` types, and the shared `*ControlResult` types. Members and JSON are unchanged; the OpenAPI schemas take the new names.
- `AdminControlAction` is gone: tenant and namespace verbs answer `ControlAction`, which gains `AlreadyInState = 6`; `VersionConflict` is 5 for every verb.
- HTTP control responses drop `message` (build text from `action` and `status`), and job controls no longer echo `jobRef`.
- `GetCheckpointsAsync`, `GetJobIdAsync`, `GetStatusAsync`, `GetInputAsync`, and `GetResultAsync` wrap their value in a response (`.Items`, `.JobId`, `.Status`, `.Input`, `.Result`); a lookup that matches nothing answers `null`.
- The enqueue contract is `EnqueueJobRequest`, `EnqueueJobResponse`, and `EnqueueJobAction`; `EnqueueBatchAsync` returns `EnqueueJobsResponse`.
- Wait results are `ChildWaitOutcome`, `ChildrenWaitOutcome`, and `SignalWaitOutcome`; `AlertDeliveryOutcome` is `AlertSendStatus`; `ActaControlDecision` is `ActaControlVerdict`; `ActaControlRequest` is `ActaControlContext`.
- Code families drop the `Job` prefix (`CheckpointKindCode`, `StepStatusCode`, `EventReasonCode`, ...), and `JobAuditLevelCode` is `DefinitionAuditLevelCode`. A stored id a newer Acta wrote decodes as the family's id-0 member instead of throwing.
- `GetOverviewQuery.IncludeSlowCounts` and the overview's `JobCount` and `SystemJobCount` are gone.
- A tag read answers `{"items": [...]}`; the input template carries its skeleton as JSON text in `templateJson` and answers 404 for an unknown job.
- A worker's last heartbeat is `LastSeenAtUtc` (`lastSeenAtUtc` in JSON) on `GetWorkerResponse` and `ListWorkersItem`, and `WorkerLastSeenAtUtc` on `GetJobExplanationLease`, the name the `workers` column has.

Schema and direct SQL:

- Migrations are `M{yyyyMMddHHmmss}_{name}.sql`, and the `migrations` table is `name` and `applied_at_utc`. Routines and views ship inside migrations; the startup installer is gone.
- `steps` and `schedules` are keyed by `(job_id, name)`: `steps_view` and `schedules_view` have no surrogate id, and a `ListSchedules` cursor from an earlier build is rejected.
- Code columns carry no value-list CHECKs, so a new code value needs no migration.
- `steps_view` and `checkpoints_view` name their decoded status `status`, as every other view does (was `state`), and `alerts_view` adds `acknowledged_at_utc`.
- Only the hot paths stay routines: enqueue, claim, complete, steps, checkpoints, signals and sleep timers, meters, the heartbeat, recovery, and retention. On SQL Server the routines and table types are named verb first (`enqueue_job`, `enqueue_jobs`, `claim_jobs`, `acta.enqueue_tags_batch`, ...).
- The SQLite outbox DDL uses `INTEGER PRIMARY KEY AUTOINCREMENT` and `STRICT`; a table from the earlier script keeps working.

### Execution engine

A worker is one claimer, its executors, and one finalizer, and the database renews only what the process holds. Nothing a consumer calls changes.

- A claim moves its rows straight to Executing: one execution path, no profiles.
- The finalizer lands up to 128 completions of any shape in one `complete_executions` call and repeats a write until it lands. A failing database stops intake instead of growing memory.
- The heartbeat renews only the executions and locks the process holds; anything else lapses to crash recovery.
- Crash recovery runs on the heartbeat: a dead worker's jobs are back within two leases, six minutes at the default heartbeat.
- An attempt cancels at its own lease deadline when renewals stop, so a database outage stops the handler.
- A definition override reaches every worker within one heartbeat.
- A claim starts where the worker's last full claim ended, so it skips the dead index entries earlier claims left behind.
- SQLite syncs every commit (`synchronous = FULL`), so the `AtMostOnce()` caveat for SQLite is gone. Single enqueues and workers with few executors pay for it in throughput, and on Windows one job at a time picks up in about 20 ms instead of 2 ([known limitations](./known-limitations.md)).
- The system slots claim at Realtime, so a Realtime backlog no longer starves them.
- Retention walks `runtimes` from a cursor instead of an index, and SQL Server no longer page-compresses `results`.

### Additions

- `JobRef`, `AlertRef`, and `WorkerRef` also parse the plain Guid behind the ref, hyphenated or not, with or without the prefix.

### Fixes

- SQL Server enqueue seeks its deduplication index instead of scanning `jobs` under `UPDLOCK`, which could escalate to a table lock.
- SQL Server enqueues of different deduplication keys no longer wait for each other: each locks its own key with `sp_getapplock`. A refused key lock raises error 51205, retried like a deadlock.
- SQL Server steps and checkpoints of different jobs no longer queue behind one range lock.
- SQL Server never escalates locks on `jobs` (`LOCK_ESCALATION = DISABLE`).
- A job's rows (`runtimes`, `results`, `steps`, `checkpoints`, `schedules`) carry no foreign key to `jobs`; `PurgeJob` and retention delete them with the job.
- The SQL Server claim no longer deadlocks with an operator verb.
- Raising or resolving an alert no longer deadlocks against a purge of its job on PostgreSQL.
- A SQL Server rate meter no longer refuses the last job of a burst.
- The overview's counts and the Failed list read indexes instead of scanning `runtimes`, and recovery reads only in-flight rows on PostgreSQL and SQLite.
- The dashboard's lists seek by namespace on PostgreSQL and SQLite, so a page costs the same at any history size.
- The overview no longer blames idle workers in one namespace for another namespace's backlog.
- `sys.alerts` skips first-attempt successes, so a failure's alert no longer waits behind them.
- The outbox relay drains a backlog in one tick, and a SQLite outbox source deletes relayed rows without scanning its backlog.
- A scoped service that throws while the attempt's scope is disposed no longer leaves the job Executing with its executor held.
- A handler cancel walks the job's descendants even when the first completion write committed and lost its answer.
- A metrics listener that throws no longer strands claimed rows until their lease lapses.
- On PostgreSQL two first starts of one step no longer fail the later one with a unique violation.
- Recovery's stale child-latch read seeks `ix_checkpoints_pending_latches` instead of scanning `checkpoints`.
- A SQLite completion stamps every row it writes with one instant.
