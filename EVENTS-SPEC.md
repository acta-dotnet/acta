# Compact events: concrete schema specification

The approved events implementation schema (step 2 of [temp-plan.md](temp-plan.md)): fifteen data columns plus the optional routing column. The final SQL Server clustering remains subject to the integrated benchmark.

## Columns and types

| Column | SQL Server | PostgreSQL | SQLite (STRICT) | Null | Notes |
|---|---|---|---|---|---|
| `event_id` | `bigint IDENTITY(1,1)` | `bigint GENERATED BY DEFAULT AS IDENTITY` | `integer` rowid | no | Identity allocation independent of retained history. |
| `namespace_id` | `int` | `integer` | `integer` | no | Sys namespace (1) for tenant events, as today. |
| `worker_id` | `int DEFAULT 0` | `integer DEFAULT 0` | `integer DEFAULT 0` | no | 0 means no worker, as today. |
| `created_at_utc` | `datetime2(3) DEFAULT SYSUTCDATETIME()` | `timestamptz DEFAULT now()` | `integer` ms epoch default | no | Unchanged per provider. |
| `entity_code` | `tinyint` | `smallint` | `integer` | no | Shared `EntityCode`. |
| `entity_id` | `bigint` | `bigint` | `integer` | no | The subject's numeric identity. |
| `event_code` | `tinyint` | `smallint` | `integer` | no | `EventCode`, byte-backed as today. |
| `definition_id` | `int` | `integer` | `integer` | yes | Set for job-subject and definition-subject events. |
| `tenant_id` | `int` | `integer` | `integer` | yes | Set for job-subject events with a tenant; null for tenant-subject events (the subject carries it). |
| `lineage_root_job_id` | `bigint` | `bigint` | `integer` | yes | Job-subject events only; `COALESCE(j.lineage_root_id, j.id)` as today. |
| `execution_number` | `int` | `integer` | `integer` | yes | Attempt facts and notes. |
| `duration_ms` | `int` | `integer` | `integer` | yes | Succeeded and failed attempt facts; null for orphaned (no measured duration). |
| `event_message` | `nvarchar(512)` | `varchar(512)` | `text` | yes | Human text only; replaces `reason_message`. Not a classification channel. |
| `details_format_id` | `tinyint DEFAULT 0` | `smallint DEFAULT 0` | `integer DEFAULT 0` | no | Registered encoding id, same registry as input/result/value; JSON is the default encoding for event details. |
| `details` | `varbinary(max)` | `bytea` | `blob` | yes | Encoded payload. Emission guidance: small, rare, no job payload bytes. |
| `bucket` | computed, see clustering | — | — | no | SQL Server candidate layout only. |

The format_id + blob convention holds everywhere: events use the same pair shape as `input`, `result`, and checkpoint `value` — no native JSON column, no DB-level JSON validation; the writer guarantees the encoding.

Checks:

- `ck_events_details_pair`: `(details_format_id = 0 AND details IS NULL) OR (details_format_id <> 0 AND details IS NOT NULL)` — today's pair check, renamed with the column.
- The emitter's synthetic byte checks apply to `entity_code`/`event_code`/`details_format_id` on PG/SQLite as they do today for byte columns.

Dropped columns and their replacement channel: `actor_code`/`actor` → `details.actor` (`sys`/`worker` implied by the code and `worker_id`; operator principal and job-id actors recorded explicitly); `job_id`/`job_ref` → `entity_code = Job` + `entity_id` (no ref repeated per event; the purge tombstone snapshots it once); `from_status_code`/`to_status_code` → implied by the event code, with `details.from`/`details.to` only where a code spans landings; `execution_status_code` → split into distinct event codes; `reason_code` → distinct event codes for alert-relevant classes, `details.reason` (kebab, inside the JSON-encoded payload) for the rest; `detail_format_id`/`detail` → `details_format_id`/`details` (pair convention kept, plural name per the payload-role vocabulary). `details.x` below always means a field of the JSON-encoded details payload.

## EntityCode allocations

`EntityCode` lists **all** entities, numbered by tens in alphabetical order of entity name. State companions share their owner's identity and get no code of their own.

| Code | Entity | Code | Entity |
|---|---|---|---|
| 10 | Alert | 80 | Namespace |
| 20 | Checkpoint | 90 | Schedule |
| 30 | Definition | 100 | Step |
| 40 | Event | 110 | Tag |
| 50 | Job | 120 | Tenant |
| 60 | Lane | 130 | Worker |
| 70 | Lock | | |

Worker lifecycle events (started/stopped/died) get the worker as subject instead of null job columns; alert ack/resolve events get the alert as subject with the job context in dimensions. Tag support remains the explicit validated subset (Tenant, Namespace, Definition, Job — unchanged). Satellite subjects keyed by composite names (schedules, steps, checkpoints) have no single numeric identity; their facts stay on the Job subject with the slot name in details, as mapped below.

## Event-code mapping

The execution block replaces today's single 41 `JobExecutionFinished` + `execution_status_code` because success and failure are distinct facts.

| Code | Name | Replaces | Columns set | details |
|---|---|---|---|---|
| 40 | `JobExecutionSucceeded` | 41 + exec 100 | execution_number, duration_ms | — (no success sentence) |
| 41 | `JobExecutionFailed` | 41 + exec 200, non-terminal landing | execution_number, duration_ms, event_message = failure text | `reason`, `to` (ready/suspended) |
| 42 | `JobExecutionOrphaned` | reclaim 41 + exec 230 | execution_number, worker_id = stale holder | `reason` (lease-expired), `to` |
| 43 | `JobExecutionYielded` | 41 + exec 150/151/152/220 | execution_number, duration_ms | `outcome` (rescheduled/suspended/paused/cancelled), `reason` |
| 44 | `JobFailed` | 41 landing terminal (to 200) | execution_number, duration_ms, event_message | `reason` |

All other codes keep their current numbers and subjects, re-expressed on the generic pair: tenant 10–12 (entity Tenant), namespace 20–22 (entity Namespace), definition 30–31 (entity Definition), job control 50–90 (entity Job), schedule 100–104 (entity Job, `details.schedule` = name), worker 120–122 (entity Worker), alert 140–141 (entity Alert, job dimensions kept), outbox 180–181 (entity Job = sys.outbox slot). Per-site mapping notes:

- Old actor/reason semantics: operator verbs write `details.actor` (principal) and nothing else (today's constant reason 40 `JobControlManual` is implied by the code); cascade cancel writes `details.reason: "parent-cancelled"`; wait timeout `"wait-timed-out"`; retire-cancel `"definition-retired"`. The `EventReasonCode` enum is deleted from events; steps get their own `StepFailureCode` enum with the same persisted values for the codes steps actually use (the `failure_code` rename in temp-plan.md).
- 75 `JobPurged`: unchanged contract — written always, in the purge transaction, entity Job with the original `entity_id`; `details` snapshots `job_ref`, `correlation_key`, operator, and reason once. This fixes the current stale comment in `PurgeJobHandler.cs` ("surviving events carry its public ref" — they don't; purge deletes the job's events first).
- 90 `JobNoteRecorded`: keeps worker/execution_number parameters; the note text moves from `reason_message` to `event_message`; the optional payload stays in the `details` pair with its caller-provided format id. A note stores the worker that wrote it, unchanged.
- 80 `JobSignalRaised` expiry suffix and child-terminal context move into `event_message`/`details` unchanged in meaning.
- 180/181 outbox evidence line stays in `event_message`.

## Recording gates

`audit_level_code` → `event_recording_code` / `EventRecordingCode` (Off 0, Failures 10, Audit 20), snapshot-copied to jobs at enqueue as today.

- **Audit**: every code above, same sites as today.
- **Failures**: 41, 42, 44, lane repair 72, and 40 when it is a recovery. The current Failures probe — reading the job's newest execution event to detect success-after-failure — is replaced by `failure_count > 0` on job state in the same completion transaction, removing an event read from the hot path.
- **Off**: nothing optional.
- **Alert overlay (rulings 6/13)**: when the definition's alert profile is enabled, the alert-required set — 41, 42, 44, and 40-as-recovery — is written regardless of `event_recording_code`, by every alert-producing writer: completion/finalizer and reclaim, all three providers. The recovery success is `failure_count > 0` before the reset, or, for a one-shot job, `execution_number > 1`. An operator restart zeroes the failure count, so the attempt number is the only completion-side signal that a restart-then-success may close an open incident. The cost is accepted: at most one extra success event per multi-attempt one-shot job (for example one that yielded first), and projecting it is a no-op when nothing is open. Recurring runs keep `failure_count > 0`, so system ticks stay silent. A first-attempt success is never alert-required.
- Tombstone 75, tenant/namespace/definition/worker/alert/outbox events stay ungated (Always), as today.

## Alert projector changes

`GetAlertableEvents` filters become code-driven: `event_code IN (40, 41, 42, 44)` with `entity_code = Job`, same namespace/horizon/cursor shape. Classification in `AlertsJob.ProjectAsync` maps directly: 40 → resolve; 44 → FinalFailure; 41/42 → FirstFailure/Threshold path. The dedup key's reason component uses `details.reason`'s kebab value, decoded in C# from the projected details payload (the SQL filter no longer needs reason codes). `alerts.last_projected_event_id` and the cursor semantics are unchanged.

## Retention and purge protection (ruling 13 safeguards)

- `purge_expired_data` gains a per-namespace **alert floor** parameter: the consumed `(created_at_utc, event_id)` cursor position, read by the retention job in C# from the sys.alerts cursor variable and passed in. Events with alert-required codes above the floor are excluded from the delete predicate. When the namespace has no enabled alert profiles, the floor is the cutoff itself (no exclusion). Poison events: the retention job collects unresolved `alerts-skip-{eventId}` markers and passes those ids as an exclusion list; they stay protected with their context until replayed or explicitly dispositioned.
- Job deletion defers: section 1 (jobs) and `purge_job` skip a job while an unprocessed alert-required event has `entity_id` = that job above the floor. Explicit purge reports the blocked condition to the caller instead of silently skipping.
- The settled projection horizon continues to govern transaction visibility; the floor governs consumption. They are different values and both apply.

## Indexes

Index names keep the `ix_events_<purpose>` style. Both clustering candidates ship PAGE compression on SQL Server as today (columnstore stays scrapped).

**Control layout (worker clustering)** — today's shape on the new columns:

- `pk_events (worker_id, event_id)`, OPTIMIZE_FOR_SEQUENTIAL_KEY
- `ix_events_lineage_timeline (lineage_root_job_id, created_at_utc, event_id) WHERE lineage_root_job_id IS NOT NULL`
- `ix_events_namespace_timeline (namespace_id, event_code, created_at_utc, event_id)` — also the alert projector's path
- `ix_events_entity_timeline (entity_code, entity_id, created_at_utc, event_id)` — replaces `ix_events_job_timeline`, now serving every subject kind, unfiltered (entity pair is NOT NULL)
- `ix_events_namespace_created (namespace_id, created_at_utc DESC, event_id DESC)` — dashboard grid

**Candidate layout (namespace/bucket/time)** — SQL Server only:

- `bucket` computed persisted `tinyint`, `worker_id % 8`; workerless events concentrate in bucket 0, acceptable because the engine writes no enqueue event and operator traffic is low.
- `pk_events (namespace_id, bucket, created_at_utc, event_id)` clustered — saves the separate dashboard feed index (reads seek 8 buckets and merge).
- Same lineage, namespace/event-code, and entity timelines as the control.

**New duration index (ruling 5)**, both layouts, all providers:

- `ix_events_duration (namespace_id, definition_id, created_at_utc) INCLUDE (event_code, duration_ms) WHERE event_code IN (40, 41, 44) AND duration_ms IS NOT NULL` (PG/SQLite: partial index, same predicate). Success-only graphs filter `event_code = 40`; all-outcome graphs take the set. Populations are stated per query; hourly P95s are never averaged into wider P95s.

PostgreSQL keeps its heap with these as plain btrees (no bucket). SQLite keeps `event_id` as rowid with the same secondary indexes (no bucket).

## Reader rewrites

- `ListEvents` + `ListEventsRow/Item`, HTTP ledger endpoints, CLI output: project the new columns; `details` decoded to text for the text-capable formats exactly as `detail_text` is today; filters gain `entity_code`/`entity_id` and lose `actor_code`/`reason_code` (actor/reason filtering moves to the details payload and is out of SQL scope for v1).
- `events_view` (the operator contract): event_id, created_at_utc, namespace (decoded), namespace_id, entity_kind (decoded), entity_code, entity_id, event (decoded), event_code, definition_id, job_name (joined), tenant_id, tenant_name (joined), lineage_root_job_id, lineage_root_job_ref (joined, null after root deletion), worker_id, worker_ref (joined), execution_number, duration_ms, event_message, details_format (decoded), details_text (decoded for text-capable formats). Decoded actor/from/to/execution-status/reason columns are dropped — those facts live in the code and details payload.
- `GetJobExplanation`: "newest reason" becomes newest of codes 41/42/44 by `(entity_code, entity_id)` reading `event_message`/`details.reason`; "last worker" query unchanged in intent (`worker_id <> 0`).
- Dashboard `executionsState.ts` builds execution rows from codes 40–44 instead of 41 + execution_status; `HISTORY_CODES` lists updated; `copyAsSql.ts` updated to the new `events_view` columns. Wire or dashboard changes run the full dashboard suite before committing.
- The Failures-gate probe in `CompleteExecutions` (all three dialects) is deleted in favor of the `failure_count` check.

## Explicitly out of scope

Partitioning (deferred, ruling 9); a global event-ID index; public ref/correlation lookup after retention (separate contract — tombstone JSON is not indexed lookup support); PG/SQLite physical tuning beyond the index list above.

Wire subject: `entityKind` (kebab) + numeric `entityId`, the documented exception to the retired-identity-names ban; joined refs stay populated while subject rows exist. No stored `job_ref`.
